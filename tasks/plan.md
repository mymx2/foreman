# Plan

一次性计划文件，不被 git 追踪。存放位置：

```
tasks/__<sub>/YYYYMMDD/NN-plan-<kebab-slug>.md
```

- `YYYYMMDD` — 创建当日日期
- `NN` — 当天序号（01、02…），plan 与对应 todo 共享同一序号
- `<kebab-slug>` — 小写英文短横线格式，概括需求的简短标识

示例：`tasks/__example-app/20260115/01-plan-add-dark-mode.md`

## 进度元信息

文件头部必须携带 frontmatter，供不读正文即可判断进度：

```markdown
---
status: draft | approved | done | abandoned
---
```

流转：`draft`（待批准）→ `approved`（已批准）→ `done` / `abandoned`。创建时设置，状态变化时更新。

## 正文结构（五要素）

计划正文参考五要素组织。结构是参考不是填空表：小任务一两行带过，要素有答案即可，不必强行分节；大型改造逐项写全：

| 要素       | 英文对照                      | 回答的问题                                                           |
| ---------- | ----------------------------- | -------------------------------------------------------------------- |
| 做什么     | Goal · Output                 | 目标、背景、交付物及其形式，改到什么程度算成功                       |
| 改哪里     | Scope                         | 影响范围、涉及模块、依赖关系                                         |
| 不改哪些   | Constraints                   | 不能触碰的文件、接口语义、配置和兼容逻辑；安全/合规/业务上的硬性约束 |
| 怎么验     | Success Criteria · Validation | 验收命令与判定标准（构建、测试、lint、手测路径）                     |
| 失败怎么办 | Stop Rules · Fallback         | 回滚方式、阻塞时的升级路径                                           |

英文对照只是参照词汇，读外部英文模板时能对上号即可，计划正文照常写中文。

长周期改造在此基础上拆条目：每条独立可验证、可回滚，按依赖排序，粒度以一次能独立合入为准。
