# Computer Flow

交付物是本地可重复运行的 Python 脚本，运行时零 AI 零 API key。

## 第一原则：先看，再动

**这个技能里最重要的一条。其余方法都建立在它之上。**

自动化失败绝大多数不是定位算法不行，而是**在错误的前提下动手**：以为还在某一页、以为窗口是某个尺寸、以为没有对话框、以为上一步成功了。这些假设没有一个能从元素列表里读出来，只有「看」能。

### 看的顺序：从外到内，四层

按这个顺序看，不要跳层。每一层的结论都是下一层的前提。

**第一层：显示器。** 先问「这台电脑有几块屏、每块多大、缩放到多少」。同一块屏的物理尺寸和逻辑尺寸可以差一倍，而应用是按逻辑尺寸布局的——1920×1080 的屏在 200% 缩放下，应用拿到的画布只有 960×540，界面会被压成紧凑布局：侧栏折叠、按钮换位置、次要项收进「更多」。**不要假设主屏缩放是 100%**，主副屏缩放相反的情况很常见（主屏 200% + 副屏 100%，或者反过来），这直接决定应用打开后落在哪块屏、拿到多大的画布。

需要记录：每块屏的物理 rect、work area、DPI、缩放比，以及换算出的逻辑尺寸。全部写进日志，出问题时第一个要看的就是它。

**先试着把应用的 DPI 修好，再考虑迁就它。** 当目标窗口的逻辑画布被压得很小（控件只有几十像素、按钮被挤出可视区），很多时候根因不是布局设计，而是**进程的 DPI 感知级别和屏幕缩放不匹配**——系统给应用一个缩小的逻辑画布，再把它拉伸显示。修这个根因比在压缩后的界面上做各种规避更划算：控件恢复正常尺寸后，语义定位、坐标点击、OCR 全都变可靠。

Windows 上的处理顺序：

1. **先查**：`GetDpiForWindow` 返回的 DPI 与窗口所在屏的实际缩放是否一致。不一致说明应用被系统虚拟化了
2. **尝试修**：给该可执行文件加 DPI 兼容性标记（`HKCU\Software\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers`，值形如 `~ DPIUNAWARE` / `~ PERMONITORV2`），然后重启应用，再查一次 DPI 是否变化
3. **改注册表前**先读并记录原值，交付说明里写清怎么恢复；这属于系统级配置，必须先得到使用者同意
4. **改不动就接受**：如果应用自己调用 `SetProcessDpiAwareness` 设定了感知级别，注册表标记会被它覆盖，外部改不了。这时才进入下一层——在压缩布局下用锚点、滚动、键盘等手段规避

判断修没修好，看 `GetDpiForWindow` 和逻辑尺寸是否变化，不要看界面"感觉"变没变大。

**工作流默认在副屏执行，不占用用户的主视角。** 用户在主屏上工作，自动化跑在副屏上是常态期望——不要为了「窗口更大、布局更完整」就把应用挪到主屏，那会打断用户正在做的事。只有当副屏逻辑尺寸不足以让业务控件直接可见、且无法通过滚动或展开解决时，才考虑迁移，并且必须先说明理由再动手。

副屏往往更小或缩放更高：物理 1920×1080 在 200% 下逻辑只有 960×540，应用的导航栏会被压缩到只剩首屏可见项，其余需要滚动或收进「更多」。这时**不要假设「导航栏里所有入口都在当前可见区域」**——先看导航栏底部是否出现「更多」或滚动条，再决定是滚动、点「更多」，还是换用键盘路径。把这一判断写进交付说明，让使用者知道该流程对副屏分辨率的要求。

**第二层：应用窗口。** 拿到窗口后先确认它落在哪块屏、物理 rect 多大、该屏缩放多少、换算出的逻辑尺寸是多少。再判断这个逻辑尺寸够不够：「够」的标准是业务要求的控件都直接可见，不需要滚动或展开。逻辑尺寸不足时不要硬点——要么调大窗口，要么改用键盘/快捷键路径，要么在交付说明里写明该流程要求的最小逻辑分辨率。

**第三层：遮挡与焦点。** 哪个窗口在前台、目标是否被更大的窗口压住、有没有模态对话框、有没有附属浮层（抽屉/气泡/下拉，它们是独立顶层窗口，不在主窗口截图里）。目标不在前台时合成点击会被前台窗口接收，而 `WindowFromPoint` 仍会如实报告"光标下面是目标窗口"——现象就是「坐标对、窗口对、就是没反应」。

**第四层：页面内容。** 现在停在哪一页、分几个区域、目标在哪、有没有"空列表""加载中""未登录"这类状态。

**抓图优先用系统截图，不要默认 PrintWindow。** PrintWindow 的卖点是「窗口被遮挡时也能抓」，代价是可靠性：对 GPU 合成的界面（Qt/CEF/Electron 一族），它可能返回**尺寸正确但内容只有一部分**的位图，而且不报错。这时 OCR 只能读出零星几个元素，定位器一路报「找不到元素」，可页面上明明看得见。

机制：进程的 DPI 感知级别与屏幕缩放不一致时，系统给应用的逻辑客户区和最终显示的物理尺寸不同；PrintWindow 抓的是应用自己的渲染缓冲区，尺寸是逻辑的，却按物理尺寸返回，内容因此只覆盖画面的一部分并被拉伸。表现就是「图的左上部分被放大铺满整张图」，右侧和下方的控件全部缺失——而图像看起来完全正常，没有黑边、没有空白条、墨迹率也在合理区间。**任何基于「图看起来对不对」的检测都发现不了它。**

- **默认路径**：`BitBlt` 抓全屏，再裁到窗口矩形。所见即所得，和用户看到的画面一致
- **只在窗口被遮挡、且必须读它内容时**才用 PrintWindow，并且要校验内容完整性（与屏幕裁剪的对应区域比对，差异过大就丢弃）
- 用 `Frame.source` 记录这次是哪种方式抓的，出问题时先看它

用户提供的屏幕截图是**最高优先级的证据**：当自己的抓图和用户看到的不一致时，以用户看到的为准，然后去查抓图链路，而不是怀疑页面或定位逻辑。判断「是不是抓图问题」最快的办法是拿同一时刻的用户截图跑一遍同样的读取流程，比对结果是否一致——差异明显时，问题一定在抓图。

**读文字有两条路，OCR 只是其一。** OCR 从像素猜文字，会有识别错误、漏字、把图标认成汉字（"工作台"被读成"品工作台"）；而且字小、色浅、被控件边框切割时经常直接返回空。

第二条路是**用应用自己的能力把文本吐出来**，结果精确、无识别误差：

- **Ctrl+A / Ctrl+C 读容器文本**：焦点在文本框、表格、列表、详情面板里时，全选复制能拿到该容器的完整文本。适合「确认页面上有哪些记录」「读取一行数据」「校验断言目标存在」。比 OCR 快、比 OCR 准
- **Ctrl+A / Ctrl+C 读整页**：焦点在页面主体时可能拿到整页文字，取决于应用是否支持
- **右键菜单 → 复制**：适合单个控件或单行
- **控件自身的复制按钮**：很多详情页、表格、日志面板带「复制」图标

使用顺序：**优先尝试剪贴板，拿不到再用 OCR**。剪贴板失败（焦点不对、控件不支持选择、结果是空）时不要卡住，直接退回 OCR，两条路互为备份。

代价与约束：
- 会**覆盖用户剪贴板**。读之前备份，读完恢复（`desktop_input.backup_clipboard` / `restore_clipboard` 已实现）
- 会**改变选择状态**（Ctrl+A 全选）。读完按一次 Esc 或点击空白处取消选择，避免影响后续操作
- 需要**焦点在目标容器内**。先用点击或 Tab 把焦点送进去，再发快捷键
- 剪贴板内容可能含敏感信息（账号、金额、编号），只在本进程内存里比对，**不要写进日志或证据文件**

这两条路在技能里的角色不同：**OCR 负责"看见界面上有什么"，剪贴板负责"精确读到某个容器里的文字"**。判断页面状态、找目标在哪，用图像；核对具体值、做业务断言，用剪贴板。

**多值同时存在是最强的页面上断言。** 单值匹配只能证明"这一个字符串在页面上"，无法区分"确实要找的那条记录"和"碰巧同名的另一条"。要求两个以上业务值**同时**出现在同一份剪贴板文本里，才能排除巧合：

- 列表页断言某条记录在结果中：同时断言记录编号和它的唯一伴随字段（金额、对方账户、创建人）
- 详情页断言打开的是正确记录：同时断言编号和标题里的业务对象
- 跨行断言：两条记录的编号同时出现在列表文本里，说明筛选结果包含这两条

实现上就是一次 `Ctrl+A`/`Ctrl+C` 拿到整页文本，然后逐项 `in` 判断——**全部命中才通过，任一缺失就失败**，并在错误信息里列出缺了哪几项。这比分别做多次单值断言快，也比 OCR 逐个找位置稳。

注意匹配前先做空白归一化：应用会用空格、零宽字符、换行把同一个编号拆开，直接比较原始文本会假失败。

用剪贴板做验证时记得它是有代价的：覆盖用户剪贴板（先备份后恢复）、改变容器选择状态（用完取消选择）、内容可能含敏感信息（只在本进程内存里比对，不写日志）。

两者的典型差异：OCR 会漏掉被控件边框切割、字号过小、对比度低的字段，也会把图标误读成汉字；剪贴板一次就能拿到容器的完整文本，包括这些 OCR 读不到的部分。**先试剪贴板，拿不到再 OCR**——这是更省时也更准的顺序。

**什么时候看**：动手做任何动作之前、改动脚本之后、每一次失败之后、以及切换阶段（导航→填表→下载）时。连续调试时尤其重要——前一次的副作用（残留对话框、焦点漂移、页面停在半路）会叠加到下一次，不看就分不清后面所有失败到底由哪一次造成。

**怎么看**：`scene.py --title <窗口标题>` 一次给出前三层的全部事实并附中文判定；再取一次窗口图像、按行读一遍文字确认第四层。两条一起看，不要只看其中一条。

**看到的和预期不符时，先回到已知状态，不要在当前错误状态上重试。** 「换个匹配模式再试一次」「把坐标调一下再试一次」是典型的错误反应——它掩盖了真正的问题，还会把状态搅得更乱。

## 通用性铁律

这份技能给的是**方法和路径**，不是某一台机器、某一个版本、某一种窗口布局的实现。使用者电脑上的应用版本、主题、窗口尺寸、显示器数量、DPI、语言都可能不同，以下任何一项都禁止写进脚本或交付说明：

- 具体窗口宽高、位置、屏幕坐标；归一化区域比例只允许作为**业务语义约束**写进 plan（如「右半区」「底部工具栏」对应的 `0.5 0 1 1`），禁止把某次运行观察到的控件位置比例当作跨机器通用配置
- 某一版本才有的控件位置、图标像素位置、菜单层级顺序
- 截图尺寸与坐标之间的固定缩放比
- 具体应用名、按钮文案以外的事实性内容（如某条业务的编号、金额、客户名）

坐标和区域一律在**运行时**从当前观察推导：先取窗口矩形，再在窗口或指定容器内定位元素，最后用当前截图尺寸换算。所有数值必须来自本次运行的观察结果，并在证据文件里记录来源。

`scripts/` 下的工具是**参考原语**，不是开箱即用的成品：它们演示如何取窗口几何、处理浮层、做唯一匹配与状态断言。接入具体应用时按本技能方法自行组合，不要假设这些脚本已经适配使用者的环境。

依赖与用法见同目录 `requirements-desktop.txt` 和各脚本 `--help`。

## 交付形态：声明式计划，不是坐标脚本

固化工作流要固化**语义目标**，不是像素。推荐三层分离：

```
业务意图（打开历史记录、按编号筛选、导出）
   ↓ 写进 plan 文件，交给使用者维护
语义定位策略（目标文字、匹配方式、变量、业务断言）
   ↓ 写进 plan 的 target/expect，不写坐标
执行机制（OCR / UIA / 浮层 / DPI / 激活）
   ↓ scripts/ 提供的原语，业务无关
```

用 `flow_run.py` 执行一个 YAML/JSON 计划：

```yaml
steps:
  - action: click
    target: {text: "${section_label}"}
  - action: fill
    target: {text: "${field_label}"}
    value: "${record_id}"
  - action: click
    target: {text: "${search_label}"}
  - action: assert_text
    target: {text: "${record_id}", match: contains}
  - action: expect_file
    expect:
      path: "${output_dir}/${record_id}.pdf"
      magic: "%PDF-"
      contains: ["${record_id}"]
```

```bash
# 先只解析目标，确认定位正确（默认行为，不点击）
python flow_run.py plan.yaml --app "<窗口标题>" --set record_id=... --observation-dir ./evidence

# 确认无误后再真实执行
python flow_run.py plan.yaml --app "<窗口标题>" --set record_id=... --observation-dir ./evidence --execute
```

计划里只允许出现语义信息：目标文本、`exact/suffix/contains` 匹配方式、变量占位符、业务断言。坐标在每次运行时由当前观察推导，所以窗口尺寸、DPI、主题、版本布局变化不需要改计划。目标文本在 plan 加载时与观察到的元素 label 走同一条 normalize 路径：CJK 字符之间的空格会被压掉（"查询 条件" 与 "查询条件" 等价），所以直接从 OCR dump 复制带空格的文本也能匹配。

**执行闸门**：`flow_run.py` 默认 dry-run，必须显式 `--execute` 才动作；`--max-steps` 限制计划步数（防误传大计划），业务行数上限由调用方的批量脚本自己实现。`--handle` 只作消歧兜底，正常路径用 `--app`（标题子串）或 `--process`（可执行名）发现窗口——句柄会变，不要把句柄写进计划。

**证据与脱敏**：默认只落结构化观察 JSON，不落整屏 PNG。需要截图证据时加 `--evidence-screenshots`，并且清楚它会把窗口内可见的个人信息一起存下来。`fill` 步骤在日志里只记录掩码后的值（保留前两位），完整值不进入 `log.jsonl`（JSONL，每行一条记录；进程被 kill 时最后一行可能不完整，reader 端逐行 `json.loads` 时 skip 掉坏行即可）。`--observation-dir` 必填，且必须放在版本库之外（如系统临时目录），不要指向仓库内。

`expect_file` 验证产物真实存在、类型正确、内容含预期业务字段，支持 `timeout` 轮询等待异步下载；不把“保存按钮点了”当成功。

## Overview

任何电脑自动化工作流都拆成「输入 → 动作 → 输出」三段，纯数据流程可以没有动作段。每段按下面的判断框架选实现方式。没有唯一正确的组合，只有适合当前场景的组合。

## 选型判断框架

**输入段**：数据从哪来、什么格式、多大？
- Excel/CSV/JSON 文件 → 按格式选库，列名映射而非列序
- Excel 文件正被用户打开编辑（锁定读不了）→ `xlwings` 连活动实例读，不用 openpyxl
- 格式不标准（BOM、单引号、尾逗号、JSONL 混注释）→ 先要真实样例文件，写预处理函数归一化，规则写死在脚本里并在样例上验证，不做运行时自适应
- 数据库 → 先确认驱动可用性（`pip list` 查），再选连接方式
- 实时抓取 → 归入动作段，不是输入段
- 读进来后要筛选/去重/排序/合并 → 归入内存数据处理，不是输入段

**内存数据处理**：读进来的数据要怎么变？
- 筛选/去重/排序/列运算 → `pandas.DataFrame`，小数据量用标准库 list/dict 推导式也行
- 多源合并同结构（多个 Excel 纵向拼接）→ `pandas.concat`
- 多源合并按关键列（两个表 join）→ `pandas.merge`
- 行列结构转换（透视/逆透视）→ `pandas.pivot_table` / `melt`
- 行内字段决定走不同动作分支（如某列值为 X 才发邮件）→ 在行级函数里写条件判断，不要拆成多个流程

**文件操作**：要不要碰文件系统？
- 批量遍历/复制/移动/重命名/删除 → 标准库 `pathlib` + `shutil`；删除/覆盖时限制在显式允许的根目录，逐一校验解析后的真实路径，拒绝符号链接逃逸和源目标重叠，dry-run 列出规范化绝对路径
- 读写文本文件 → `pathlib.Path.read_text/write_text`，显式指定 `encoding="utf-8"`（Windows 中文环境默认 GBK）
- 监控某个目录的文件变化 → 交给系统定时任务按分钟级调度拉起脚本比对（Windows `schtasks`、mac `launchd`、Linux `cron`），不要写 while True 常驻轮询

**动作段**：操作发生在哪个载体上？
- 纯 API 能做 → 优先 API 而非 GUI（更稳、更快、不受界面状态影响）
- 桌面 GUI：先按「窗口 → 完整控件树 → 可操作控件」三层探测，不能用浅层树或技术栈名称判断语义能力。Windows 用 `pywinauto` UIA 读取控件树；Qt 应用也要检查完整后代节点，确认目标确实未暴露 `name/auto_id/role/value/action` 后才降级。语义定位优先使用稳定标识和控件动作，其次才是元素矩形点击。目标无可用语义时，按「窗口/容器语义锚点 → 该区域截图/OCR 定位 → 客户区相对坐标输入」降级；UIA 连窗口都找不到才用 Win32 `EnumWindows` 找窗口。macOS 优先 Accessibility API 与 `AX*` 属性，Linux 优先 AT-SPI2（如 `pyatspi`）；不可用时才走 `pyautogui` 坐标 + 键鼠 + 截图比对，窗口管理 mac 用 AppleScript、Linux 用 `xdotool`。所有平台都在交付说明中标注自动化稳定性等级
  - **定位优先级链**：`AutomationId` > `Name`（可见文本）> `ClassName + index` > `XPath`。越靠左越稳。plan 里优先写 `target: {auto_id: "btnSave"}`；只有拿不到 AutomationId 时才退回 `text`。AutomationId 不受语言切换、文案改版影响，是唯一在跨版本时仍然可靠的定位键
  - **UIA 语义能力按框架差异很大**，探测前先按目标框架预判，不要一上来就假设拿得到稳定 id：
    | 框架 | AutomationId 可用性 | 说明 |
    |---|---|---|
    | WPF | 高 | XAML `x:Name` 直接映射为 AutomationId |
    | WinForms | 较高 | `AccessibleName` 即 AutomationId |
    | UWP / WinUI 3 | 高 | 微软第一方完整支持 |
    | Qt 6.x | 高 | 无障碍默认开启 |
    | Qt 5.15+ | 较高 | 无障碍模块完善 |
    | Qt 5.7–5.14 | 一般 | 需先设 `QT_ACCESSIBILITY=1`，`objectName` 常需手工补 |
    | Win32 / MFC | 一般 | 有控件 ID，常需按文本匹配 |
    | 自绘（`paintEvent` / `QGraphicsView` / `QOpenGLWidget` / 游戏引擎） | 无 | 内部完全不暴露，只能走 OCR/图像/坐标 |
  - **参考实现目前只覆盖 Windows**：`scripts/` 下的截图、浮层枚举、DPI 处理均为 Win32 实现；macOS/Linux 需按上面的对应 API 自行实现同等能力，不能直接复用这些脚本
- 桌面 GUI 遇到系统对话框（文件选择框、打印框）→ Windows 用 pywinauto `Desktop(backend="uia").windows()` 找独立窗口；mac 用 AppleScript `tell application "System Events"`；Linux 用 `xdotool search --name` 找窗口后 `key`/`type`
- 目标应用未启动 → 不要假设它已经在跑。plan 首步写 `launch`，按名称令牌查找安装位置（App Paths 注册表 → Uninstall 注册表 → 开始菜单 → 常见安装目录），启动后轮询等待主窗口出现。查找顺序按"可执行文件优先"排序：同目录下的 `updater`/`uninstall`/`elevate`/`scheme` 一类辅助程序必须排在主程序之后，否则会启动错的东西。启动是真实副作用，`flow_run.py` 要求显式 `--allow-launch` 才执行；`launch` 步骤返回的窗口句柄会替换后续步骤的目标窗口，所以 plan 里不用写死句柄
- Excel 应用本身（执行 VBA、刷新图表/透视表、导出 PDF、写数据后要公式重算）→ `xlwings`，不用 openpyxl；大批量写入时先关自动重算，写完手动 `calculate()`，再恢复。xlwings 不支持 WPS——没装 Office 但装了 WPS（Windows）时改用 `win32com.client.Dispatch` 直接驱动（先试 `KET.Application`，失败回退 `ET.Application`，再失败查注册表；注意 WPS 12.1.0.22529/22525 两个版本 COM 接口整体失效，需回退 WPS 版本）。WPS 个人版无 VBA 支持，透视表/宏/公式重算做不了，退回 openpyxl 操作文件并声明放弃这些能力。mac/Linux 上 WPS 无稳定自动化接口，退回 openpyxl
- 网页：Playwright，但需要登录态复用时优先 `launch_persistent_context` 而非每次登录
- 纯 API：requests，会话保持用 Session
- 发布/上线类动作（发邮件、发 webhook、写数据库、调 API 写操作）→ 默认先演算（dry-run 或测试记录），显式确认后再执行
- 混合载体（如读 Excel 后既填网页又发 API）：按行级粒度拆成独立动作函数，每个函数只操作一个载体
- 同一载体上的连续操作合进一个函数（如填表单的所有字段在一个 `fill_form` 里完成），不要每个字段一个函数来回切换焦点
- 目标是列表类（表格行、相似按钮、商品卡片）→ 先拿相似元素列表再遍历，不要逐个定位
- **先看屏幕再动手，这是每一步的前置条件，不是出问题时才做的补救**：解析到的元素列表、坐标、状态摘要都只是页面的**推论**，不是页面本身。开始任何动作循环之前、以及每次失败之后，先取当前窗口图像并**实际读出页面上有什么**（OCR 文本按行还原、关键区域裁剪查看），确认「我现在在哪一页、这一页有哪些控件、目标在不在」。跳过这一步的典型症状是拿着一分钟前的页面假设继续操作：在消息页上找筛选框、在已关闭的抽屉上找下载图标、把残留的对话框当成主界面。发现页面与预期不符时，先回到已知状态再继续，不要在错页面上重试
  - 元素列表数量对不上、某个 label 突然消失、点击后没变化——这些都是「该看一眼屏幕」的信号，不是「换个匹配模式再试」的信号
  - 调试期尤其如此：每改一版脚本、每换一个匹配策略，先看屏幕确认当前状态，再决定下一步。连续盲试会把前一次的副作用叠加到下一次，最后连失败原因都分不清是哪个操作造成的

- 自绘控件要读文字（老软件截图取数）→ OCR 例外分支：`paddleocr`（`pip install paddleocr`，中文准；注意 3.x 后模型需单独下载，Python 3.14 不支持 paddlepaddle）或 `rapidocr`（`pip install rapidocr`，轻量约 80MB，CPU 快），不要用 `pytesseract`（中文效果差）

**目标驱动的探索**：不能把流程退化成按用户给出的文字逐个查找。先根据语义目标拆解业务状态与完成条件，再观察当前 UI、枚举候选入口和可用动作，按状态转移选择下一步。每一步保留当前状态、候选集合、排除理由和预期后置状态；精确文字、稳定 ID、OCR 只用于定位与消歧，不代替业务决策。找不到候选时先调整观察范围、滚动或返回上级状态，禁止把最相似 OCR 结果当成目标。涉及审批、支付、发送、删除等业务动作仍需明确授权和最终目标校验；开放式探索不扩大权限。

**先发现，再操作**：自动化从发现开始，不从坐标开始。先用 `discover.py` 枚举显示器、虚拟屏范围和候选窗口（按标题或进程名过滤），确定唯一目标窗口，再取它的几何和观察。句柄、窗口位置、显示器布局都会变，发现步骤必须在每次运行时执行，不能缓存上次的结果。

**「看屏幕」不是读 OCR 文字，是建立整个场景的认知**：人看一眼屏幕就知道有几块显示器、哪个窗口在前台、每个窗口多大、谁压在谁上面、有没有弹出对话框。这些东西没有一项会出现在元素列表里，却直接决定下一步能不能点。开始动作循环前、以及每次失败后，用 `scene.py` 输出一次场景摘要再动手：

- **显示器与缩放**：窗口在哪块屏、该屏 DPI 是多少。200% 缩放下 1950×1200 的窗口**逻辑尺寸只有 975×600**，界面会被压成精简布局——侧栏折叠、按钮换位置、某些项要滚动才出现。这时用物理坐标推算的点击位置会整体错位，而且是静默的
- **前台归属**：不是目标窗口在前台时，合成点击会落到前台窗口上。`WindowFromPoint` 仍会如实报告"光标下面是目标窗口"，于是现象变成「坐标对、窗口对、就是没反应」
- **遮挡关系**：比目标大且 Z 序更靠前的窗口会盖住它。被盖住时不要点，先激活
- **模态对话框**：任何 `#32770` 出现都意味着当前页面被阻断，必须先处理掉
- **附属浮层**：抽屉、气泡、下拉是目标的子窗口，不在主窗口截图里

`scene.py --title <窗口标题>` 一次给出上述全部事实，并对异常项给出中文判定（"目标不是前台，合成点击会被前台窗口接收"这类），照着判定逐条处理，不要靠元素数量推测状态。

**改动脚本后、跑验证前，先执行一次 `scene.py`**。这一步不是为了调试方便，而是因为连续调试会把前一次的副作用（残留对话框、焦点漂移、页面停在半路）叠加到下一次，导致后续所有失败都归因错误。

**前台激活要强制，不能只请求**：`SetForegroundWindow` 在后台进程调用时会被 Windows 拒绝，`WindowFromPoint` 仍会正确报告目标窗口在光标下，但点击事件被真正的前台窗口吃掉——这是"看起来什么都没发生"的最常见原因。可靠做法是 `AttachThreadInput` 附加到当前前台线程再调用 `SetForegroundWindow`，完成后解除附加。窗口已被还原且可见但焦点申请被拒时，截图和命中测试仍然可用，不必让整个流程失败；只有需要往具体输入框打字时才必须要求真正拿到焦点。

**Qt/自绘桌面闭环**：UIA/Qt 容器负责窗口、容器、弹窗归属和输入边界；系统截图负责用户可见状态；OCR/图像匹配只在容器内产生候选。每次动作前记录 `snapshot_id`、窗口矩形、截图尺寸、DPI/坐标映射和目标候选；动作后同时检查系统截图可见性、目标区域状态和业务结果。精确文本/图标是定位手段，不是业务目标；业务目标必须由完成条件断言。

**桌面输入与窗口状态**：动作协议至少覆盖这些类别，按场景选用，不为覆盖而堆砌：
- 鼠标：单击/右键/双击、滚动、拖拽和框选。目标按语义或当前区域快照定位；双击和右键后必须验证选中状态或菜单，滚动后重新观察列表，拖拽/框选记录起止点、所属区域和最终选区
- 键盘与剪贴板：输入文字、方向键/Tab/Escape/Enter、组合键、复制/剪切/粘贴。先确认焦点控件和预期快捷键作用域，再发送按键；读取剪贴板验证复制结果，粘贴后验证控件值。剪贴板可能含敏感数据，只在必要时读写，完成后恢复或清理本次写入的内容
- 弹窗与焦点：每次动作绑定具体窗口句柄；预期弹窗出现时重新枚举窗口，验证其所属进程、标题和类型，关闭后重新绑定主窗口。非预期弹窗不得默认确认或丢弃修改，保存证据并按业务规则处理
- 多窗口与浮层：抽屉、滑出面板、气泡、下拉菜单常是**独立顶层窗口**（`GW_OWNER` 指向主窗口），不在主窗口截图和主窗口状态摘要里。动作后必须按同一进程 + `GW_OWNER` 枚举子窗口，把新出现的可见浮层纳入观察和断言；只比较主窗口摘要会把“抽屉已打开”误判为 `no_state_change`
- 浮层输入：点击浮层内的控件前必须先把**该浮层窗口**激活（`ShowWindow(SW_RESTORE)` + `SetForegroundWindow`），否则点击会落到下方主窗口。浮层窗口若有独立 DPI（如 192），其 PrintWindow 图像尺寸通常等于客户区物理像素，坐标可按窗口原点直接换算；换算后仍须验证鼠标实际落点
- 浮层跨进程：**按 `GW_OWNER` 链枚举时必须遍历全系统窗口，不能先按宿主进程 ID 过滤**。下载组件、云盘、打印服务常由独立进程托管系统对话框，按 PID 过滤会静默漏掉「另存为」「打开」这类窗口——表现为"点了下载什么也没发生"，实际上对话框已经弹在别处。动作后要拿「动作前浮层句柄集合」做差集，等新窗口出现再继续
- 动作后必须检查新窗口：click 之后不要只重新观察主窗口。先记录动作前的浮层句柄集合，动作后 `wait_for_overlay` 等新增窗口；检测到新窗口就把它记进日志并作为下一步的操作目标，检测不到才认为"没有弹窗"。跳过这一步会在主窗口上继续操作，把同一个对话框再触发一次，留下孤儿窗口
- 人工接管：交互式运行前明确提示用户暂时不要操作鼠标键盘；暂停、超时或窗口状态异常后，所有旧观察作废，重新观察再继续。桌面输入共享全局鼠标和焦点，不能假定脚本独占这些资源
- 执行互斥：任何共享桌面输入的脚本必须持有跨进程独占锁（`O_EXCL` 锁文件 + 过期回收），第二个会话直接失败而不是抢焦点。锁在退出时释放，崩溃后按超时回收；回收和释放都必须基于自己创建时读到的锁内容，避免误删他人重建的锁
- 用户中断：必须提供不依赖当前动作完成的独立中断通道。推荐后台线程监听 ESC 的 `GetAsyncKeyState`，按下即设置中止标志；中止标志按会话（如目标窗口句柄）分文件，两个并行自动化会话不得共用同一标志文件；每个动作前后检查该标志，命中就以专用退出码结束，不要吞掉中断当作普通失败
- 遮挡定位：点击前用 `WindowFromPoint` 判定落点归属，被其他窗口覆盖时中止并记录遮挡窗口的句柄、标题和进程。仅说“不可见”不足以诊断；必须指明是谁挡的
- 自绘控件 icon+label 布局：UIA 可能只暴露 icon 子树而 OCR 识别旁边的文字 label，两个元素 label 相同但中心互不包含，合并会失败、`select` 抛歧义错误。这时用 `sources: [uia]` 强制单源，或用 `region` 缩小到目标所在子区域——不要把这当成"坐标系算错"去调坐标
- 快照过期：每次观察生成快照 ID 并绑定到元素；动作前校验元素所属快照，过期元素返回 `STALE_REF` 并要求重新观察，禁止用旧坐标重试
- **定位分三档，按「元素位置由什么决定」选，不是一律走语义定位**：
  - **位置由布局决定**（导航栏、工具栏、表单标签、固定按钮）→ 缓存坐标。这类元素在同一个应用版本里不会动，每次全屏 OCR 重找它纯属浪费——实测一张 3200×1904 的窗口 OCR 一次约 4 秒，而校验一个缓存坐标约 1 毫秒。缓存的是**客户区内的相对比例**（`(x-left)/width`），所以窗口移动、缩放、跨屏拖动到不同 DPI 后仍然有效；不能存屏幕绝对值
  - **位置由数据决定**（表格行、列表项、搜索结果、动态卡片）→ 不能用固定坐标，位置随行数、排序、分页漂移。但表格通常**间距规则**：动作列 x 固定、行高恒定，一次观察量出行高后，第 N 行 = 首行 + N × 行高，不需要每行重新 OCR
  - **位置由系统决定**（原生对话框、系统控件）→ UIA，控件有稳定 `AutomationId`，比任何像素方案都准
  - 只有以上三档都不成立时才退回全屏 OCR
- **缓存坐标必须带校验，没有校验的缓存坐标等于硬编码**：点击前对被点位置取一小块（约 72×72）重新截图，与缓存时记录的指纹比对。指纹不能只用平均颜色——按钮面和旁边空白都是纯白，会互相通过；用「小网格均值 + 边缘密度」，它能区分"这里有图标/文字"和"这里是空白"。实测同一位置偏移 5px 差异约 0.04、偏移 20px 约 0.13，把容差设在 0.06 附近即可放行像素级抖动、拦住真的错位。校验失败就丢弃该条目、退回语义定位并重新记录，不要带着怀疑的坐标点下去
- **OCR 成本随面积增长，能裁剪就别全屏**：同一张图，全窗口 OCR 约 3.9 秒，只裁右侧筛选区约 1.5 秒。要判断某个区域的状态时，只对那一块截图 OCR；只在确实需要整个页面语义时才全屏
- **只读流程和破坏性流程的容错档次不同**：导出、查询、查看这类可以重来，坐标缓存的误点代价是浪费一次运行；删除、提交、审批这类不可逆操作，即使坐标命中也要再断言业务结果，不能只靠"点到了"就认为完成
- **交互态才出现的控件**：静态截图只反映静息态。很多界面把次要操作藏在交互态里——同一位置在不同状态下可能是不同控件：图标悬停后变成清除按钮，列表行悬停才出现删除，工具栏悬停才显出文字标签，输入区在有值且悬停时才长出清空按钮。只按静息态写 plan 会漏掉这些操作，或误判某个图标的功能
  - 发现方法：对目标区域分别取「静息态」和「交互态」截图对比——悬停用移动指针，聚焦用点击或 Tab 移入——逐点算像素差异。噪声会形成一个稳定底值（整行所有点都有相近的非零差异），真正响应交互的点会明显高出一截；按这个台阶判热点，不要用绝对阈值。找到热点后放大确认它到底变成了什么形状，再决定能不能点
  - 写进 plan 时必须注明三件事：静息态是什么、需要什么条件才出现、出现后能做什么。只写"点某某右侧"会让维护者按静息态点空
  - 结论只在当次观察有效：控件的位置和出现条件随数据状态变化（值被清空后按钮就退回静息态）。落笔前重新验证一次，不拿几分钟前的结论当事实
  - 清空一类操作优先用局部控件而不是全局重置：全局重置往往连带清掉用户已经填好的其它条件，局部清除只影响它所属的那一组
- 动作与观察分账：注入成功只代表 `sent`，不代表页面变化；变化必须由动作后的重新观察得出 `observed`。这两个字段必须分别记录，不能用同一个 `changed` 布尔值代替
- 最小化与离屏：`GetWindowRect` 返回 `-32000/-16000` 一类哨兵坐标即窗口最小化，必须 `ShowWindow(SW_RESTORE)` 并确认不再是 `IsIconic` 后再动作；窗口超出屏幕时只使用可见裁剪区域坐标，越界目标直接失败
- DPI 与物理坐标：动作进程先 `SetProcessDpiAwareness(2)`，全程只使用一套物理屏幕坐标；窗口矩形、截图尺寸、OCR 坐标之间的换算必须显式记录来源，禁止把逻辑像素和物理像素混用
- 坐标与选区：统一使用当前观察到的窗口矩形、截图尺寸和 DPI 缩放，动作输入前把 OCR/截图坐标换算回输入坐标；点击目标控件前先激活目标窗口。截图、窗口矩形、DPI、焦点或页面状态变化后，旧坐标、元素引用和选区作废。框选之外的内容不得作为后续动作目标
- 双证据截图：窗口内图像用于定位控件，系统截图用于验证用户真实可见画面。目标在系统截图中不可见、被遮挡或焦点不属于目标窗口时，动作失败，不得凭窗口内图像盲点；最终验收必须同时保存结构化状态、窗口图像和用户视角截图
- 动作断言：后置断言必须读取动作后重新观察的状态，并限制在预期变化的作用域内；输入框、筛选框或列表中原有的文本不能证明详情/提交/下载已完成。失败类型与动作失败分开记录；点击或输入返回成功只表示动作已发出，不表示目标状态成立。click 类动作的预期页面转移未发生时记录 `no_state_change` 并中止后续步骤，断言区域不正确时记录 `assertion_scope_invalid`；已通过 `expect.target` 显式断言的步骤、以及 fill/key 等不必然改变可见状态的动作不适用 `no_state_change` 中止。`expect.target` 不能引用点击目标本身——那等价于"点击前存在"，恒真；要堵"目标本来就在屏幕上"的假阳性，用 `expect: {target: {...}, not_in_before: true}` 强制要求断言元素在动作前的观察里不存在
- 停滞检测：记录每个动作的 `action_id/selector/point/state_digest/expectation`。同一目标在同一状态下动作后状态摘要未变化即标记 `no_state_change`；同一状态连续 2 次停滞必须停止试错，转入诊断分支（焦点、遮挡、坐标系、输入路径、应用能力边界），诊断完成后才允许更换一种已验证的输入方式。滚动、翻页、切换标签等改变了可见内容的操作属于新的观察状态，不累计停滞；禁止用不同坐标对同一语义目标机械重试，禁止要求用户发现脚本绕圈

**输出段**：结果给谁看、什么形态？
- 人看 → 追加写 CSV（中断不丢）或格式化 xlsx
- 系统消费 → 写数据库或调 webhook
- 通知 → 邮件用 465 SSL（国内场景更稳），IM 用钉钉/企微 webhook；钉钉发图需走图文/markdown 消息，不能裸发 webhook text

**任务队列与断点续跑**：流程长、可能中断、要续跑？
- 任务来源是文件 → 处理完一行就在结果 CSV 追加一行并记录输入行号，重跑时跳过已处理行
- 任务来源是动态队列（API 拉取、消息订阅）→ 本地 SQLite 存任务状态（`sqlite3` 标准库），字段至少含 `id/status/retry_count/last_error`
- 失败重试 → 行级 try/except，失败行标记状态后继续下一行；重试上限按场景定（网络超时 3 次、应用未响应 2 次），超过标记为永久失败
- 失败分类 → 数据问题（输入行缺列、格式错）不重试直接标记；系统问题（网络超时、应用未响应）才重试。外部写操作还要区分「确定未执行」和「结果未知」：邮件、webhook、订单提交等请求超时后不得盲目重试，先用幂等键或业务查询确认未执行，无法确认时标记结果未知并停止该动作
- 破坏性批量操作（批量删除、批量覆盖、大批量写）→ 先演算（dry-run 只统计不写），给用户确认后再执行
- 需要可回放 → 每次演算/执行都在本地落一条记录（时间、动作、行数、结果），GUI 关键节点截图落盘作为留证

**触发方式**：固化后怎么让它跑起来？
- 手动跑 → 技术用户给 `python script.py`，非技术用户附启动脚本（Windows `.bat`、mac `.command`、Linux `.sh`）或打包可执行文件
- 定时跑 → 系统定时任务（Windows `schtasks /create`、mac `launchd`、Linux `cron`/`systemd timer`），不要写 while True + sleep 的常驻脚本
- 文件变化触发 → 交给定时任务按分钟级调度拉起比对，不要上 watchdog

## Outcome Contract

- **Outcome**: 本地可重复运行的 Python 脚本，完成规定动作，运行时零 AI 零 API key。
- **Done when**: 涉及 GUI 时脚本在目标应用各种初始状态下都能跑通（未启动/最小化/弹窗遮蔽/非最大化），干净状态下两次独立运行结果一致，已有状态下第二次运行不重复执行、不追加重复结果；纯数据/API 流程同样区分干净重跑与续跑验证。核心定位器、真实动作和业务断言有 `# TODO` 时只能交付未验收草稿，不能标记完成。
- **Evidence**: 逐行执行结果 + 状态校验（HTTP 状态码、表单提交成功提示、发送结果）；两次完整运行的退出码。
- **Authorization**: 探测、写脚本、跑脚本可直接做；结束/重启目标应用进程前需用户确认；破坏性批量操作和花钱/不可逆操作执行前需用户确认（确认 = 用户在对话中显式回复，且记录进审计日志）。一次确认只覆盖当次动作的具体目标与数据量：输入数据、目标对象或执行范围变化时重新确认；定时任务和 `.bat` 入口不得复用过去的确认
- **Run gates**: 交付脚本必须保留运行时闸门，而不是只在搭建期做过演算：不可逆动作默认 `--dry-run`，实跑需显式开关；实跑前校验待处理条数与演算结果一致，超出则拒绝执行；单次运行条数设上限，超出要求显式提高配额

## Process

**完整走通的例子见 `references/worked-example.md`**：一个多步导航 + 表单筛选 + 列表操作 + 浮层 + 系统对话框 + 文件产物的流程，从环境探测到双屏验收的完整过程，含 8 个典型坑的具体现象与修法。所有应用名和数据都是占位值，看的是步骤和判断方式。

**外部模式参考见 `references/external-patterns.md`**：四个公开仓库提炼的「撞墙字典」（测试沙箱环境重定向、Job Object 进程遏制、ffmpeg 录屏、Qt QComboBox/`with_spaces` 坑、密码管理器黑名单、golden image 断言）。全部**未在我们环境验证**，撞墙时先查它再自己摸索；采纳前做最小验证，验证结论回写该文档。

**调试节奏：短探测优先，不要反复跑全流程。**

改一行代码就跑一次完整流程，是最慢也最伤状态的做法：一次全流程要几十秒到几分钟，每次都把界面带到不同的中间状态，失败原因被前一次的副作用叠加，最后连「是哪个改动导致的」都分不清。

正确节奏是把验证拆成**秒级的最小探测**，每个探测只回答一个问题：

1. **只测一个原语**：抓一次图要多久、OCR 出几个元素、某个坐标点下去有没有反应。单次运行控制在几秒内
2. **探测不改变状态**：读图像、读元素、算坐标都可以反复做；只有确认坐标正确后，才做一次真实的点击
3. **一次只改一个变量**：坐标错了就只调坐标，别同时改等待时间；否则通过或失败都说明不了问题
4. **确认这一段成立，再跑下一段**：定位 → 点击 → 页面变化 → 下一个控件，逐段确认。全部段落各自验证过之后，才跑一次完整流程做验收
5. **完整流程只用于验收，不用于调试**：它验证的是「组合起来是否成立」，不承担「找出哪一步坏了」的职责

判断标准：如果一个探测需要超过 10–15 秒，说明粒度太粗，应该继续拆。超时设置也应与之匹配——点击类操作给 2 秒足够，给 20 秒只会把确定性失败拖成慢失败。

1. **拆解场景**。把需求拆成「输入 → 动作 → 输出」三段（纯数据流程可以没有动作段），按上面的判断框架写出每段的实现方式和理由。完成标准：明确每段用什么库、操作哪个载体、为什么这样选
2. **探测目标**。桌面应用 Windows 用 pywinauto UIA 枚举完整控件树，macOS 优先 Accessibility、Linux 优先 AT-SPI2；语义不足时补充窗口截图或区域 OCR。输出结构化观察记录：目标窗口、`snapshot_id`、元素 `ref/name/auto_id/role/value/bounds/source`。**截图必须实际打开检查，保存成功不等于已看图**——先描述清楚这一页上有什么、目标在哪，再开始写定位器。网页用 Playwright 打开确认定位器可用；API 试一个最小请求确认认证方式；数据库确认驱动和连接串。探测不到真实控件时（应用未装、界面未开放），生成带 `# TODO: 确认定位器` 标记的真实动作函数，不要写 print 假存根——假存根会让脚本跑通了却什么都没做。完成标准：每个动作有明确的定位/调用方式或 TODO 标记
3. **搭建动作链**。按输入数据的粒度（通常是一行）组合动作，每个函数只做一件事。GUI 使用 `observe → resolve → act → wait/assert`：从一次新鲜观察中唯一定位，0 个或多个匹配均失败；动作前重新确认目标状态，动作后断言业务结果，不能用固定 sleep、`uiChanged=true` 或截图回执替代成功判定。涉及破坏性批量操作或花钱/不可逆动作时，先实现 dry-run 版本（只统计不写），和用户确认后再接真实执行。完成标准：单行数据能完整跑通并读到预期结果，dry-run 输出合理
4. **固化入口**。主脚本读输入、逐行执行、记录结果。入口形态按用户使用方式定：技术用户给 `python script.py`，非技术用户附启动脚本（Windows `.bat`、mac `.command`、Linux `.sh`）或打包可执行文件。完成标准：干净状态下连续两次运行输出一致；已有状态时验证的是不重复执行，两者不可混用
5. **回归验证**。涉及 GUI 时模拟各种初始状态（应用关闭/最小化/弹窗/非最大化）；纯数据流程验证异常输入（文件缺失、空文件、列缺失）。完成标准：正常场景全过，异常场景有明确报错而非静默失败

## 关键技术决策

| 场景 | 做法 | 原因 |
|---|---|---|
| 输入列顺序可能变化 | 按表头名映射 | 用户加列/调列序不影响脚本 |
| 输入文件的关键约束（列名、编码、分隔符） | 搭建期和用户确认后写死在脚本里，不做「猜列名」兜底 | 猜错了静默跑出垃圾结果比直接报错更糟 |
| 结果落盘/webhook 通知 | 优先用 mock、沙箱或本地预览验证；向真实目标发测试记录前同样确认目标与内容 | 测试消息和测试写入也有真实副作用 |
| 凭据（密码/授权码/token/webhook key） | 环境变量或 `.env`，且 `.env` 必须进 `.gitignore`，交付前 `git check-ignore .env` 验证 | 「写在 .env 但 .env 被提交了」是最高频事故 |
| 非凭据环境值（URL/路径/阈值/开关） | 集中到一个 Config 文件（`.env` 或 `config.ini`），不散落在代码里 | 环境迁移时改一个文件，不用翻代码 |
| 等待元素出现/消失/属性变化 | 显式等待（Playwright `wait_for_selector`、pywinauto `wait_until_passes`、自绘界面轮询截图比对），任何等待循环必须有超时上限并抛错；超时上限用秒（等待类）或次数（重试类），按场景选；轮询间隔 ≥ 单次轮询操作耗时（轻量属性读取 0.2s、截图比对 0.5s、OCR 2s）；确知节拍必须用 sleep 时注释 why；窗口级等待（等弹窗关闭、等主窗激活）同样适用 | 轮询状态而非假设时间，无界轮询是偷懒实现 |
| 单步操作的超时预算 | 按操作性质分级：点击/按键/激活窗口这类瞬时动作 **2 秒**足够（含一次重试），属性或状态读取 **3 秒**，元素出现等待按业务实际（5–30 秒），OCR 轮询单轮 ≥ 2 秒但总时长受业务约束。**默认值不能一律给 20–30 秒**——点击等 25 秒不仅浪费，还会把「真的点不到」和「点得慢」混为一谈 | 超时是失败信号的上限，不是耐心指标；给太长的超时会把确定性失败拖成慢失败，掩盖真正原因 |
| Flutter/Qt 编辑器不接受语义定位键入 | Windows `clip.exe` / mac `pbcopy` / Linux `xclip` 写剪贴板 + Ctrl+V，备选平台原生 API | 自绘控件不实现 TextPattern/ValuePattern，剪贴板是绕过该接口的 workaround |
| 窗口最小化时连不上 | 先 `ShowWindow(SW_RESTORE)` 并确认 `IsIconic` 为假，再重新观察；`findwindows.find_elements(..., visible_only=False)` 只用于发现，不代替恢复。mac AppleScript `tell application ... to activate`，Linux `xdotool search --name ... windowactivate` | 最小化窗口的 `GetWindowRect` 返回哨兵坐标，任何据此换算的点击都会落到屏幕外 |
| 自绘编辑区无语义定位节点 | 窗口客户区相对坐标 + 脚本启动时断言窗口尺寸固定且已知（优先最大化；不可最大化时 resize 到校准尺寸或显式报错） | 相对坐标在窗口移动后仍有效，尺寸变化会失效 |
| UIA 拿到元素矩形但元素不可点击 | 用元素矩形内相对位置锚点 + 偏移：`rect = elem.rectangle()`，锚点选角/边中点/中心（容器型元素不用中心，中心常命中错误子元素），偏移为相对锚点的像素值；点击前重新取矩形（列表滚动后旧矩形失效） | 中心点在容器型元素上常点到错误子元素；矩形随布局变化 |
| 每次运行前 | 新建干净标签/表单 | 上次填写的数据、焦点位置、弹窗等残留状态会让脚本行为不确定 |
| 动作后页面看似没变 | 先查浮层：按同进程 + `GW_OWNER` 枚举独立顶层窗口（抽屉/滑出面板/气泡），再判断是否真的无变化 | 浮层不在主窗口截图里，只比较主窗口摘要会得出错误的 `no_state_change` |
| 浮层内控件点不动 | 激活浮层窗口（`ShowWindow(SW_RESTORE)` + `SetForegroundWindow`）后再点击，并回读光标落点 | 未激活的浮层被主窗口遮挡，点击会穿透到下层 |
| 批量发邮件/webhook | 按服务商限额定间隔，个人 SMTP 注意日限额 | 避免触发频率限制 |
| HTTP 请求 | 必设 timeout，默认 10s | requests 默认无限等待，脚本挂死 |
| 结果落盘 | 追加写而非一次性写 | 中断后已处理行不丢 |

## Common Rationalizations

- 「UIA 枚举不到控件就是应用不支持自动化」——先检查窗口是否最小化，再确认是不是 Flutter/Qt 自绘
- 「直接在用户当前标签页操作更省事」——残留状态让脚本行为不确定
- 「中心点最直觉所以用中心」——容器型元素的中心常命中错误子元素，该用角或边中点
- 「查询返回 0 条说明这个编号不存在」——先看有没有其它筛选条件还开着。编号和日期区间常常是与关系，编号在、但完成时间不在区间内就会查出 0 条；空结果先复位其余条件再验一遍，别急着判定数据不存在
- 「文件存下来了就是成功」——文件名对不代表内容对。列表有多条相似记录时，最容易发生"打开的是 A、导出的是 B"；必须解析产物内容核对业务主键

## Red Flags

- 整批操作共用一个 try/except，一行失败全批中断
- 屏幕绝对坐标而非「当前窗口矩形 + 元素相对位置」推导出的坐标（未做 DPI 换算的裸屏幕坐标同样禁止）
- 无界等待循环（无超时上限的 while True 轮询）

## Verification

每个动作函数写完后立即在真实目标上验证一次。最终交付前跑两遍完整流程，第二遍用于发现状态残留问题。

**交付前整体验证**覆盖三个维度：
- 功能：每行输入都产出了预期结果（HTTP status、响应 JSON 里的业务 code、表单提交成功提示）
- 韧性：中断后重跑能续上，已处理行不重复
- 边界：输入文件缺失/空文件/列缺失时有明确报错

**结果判定纪律**：分开记录「动作已发出、截图已保存、图像已检查、行为已验证」。GUI 业务成功以目标状态断言为准（控件值、数据库/文件记录、可见业务编号），截图只作辅助证据且必须实际打开检查；不看 stdout 日志级别或「没报错就是成功」。每步记录目标、结构化元素、动作结果和断言，失败时保存脱敏截图、当前步骤和窗口标识。

**不可逆流程的验证例外**：提交审批、下单、付款、发送通知这类动作没有可回滚状态，「跑两遍」等于重复执行。这类流程用「一次完整执行 + 幂等校验」代替重复运行：验证提交后的唯一性（订单号、审批编号只出现一次）、验证重复触发被系统拒绝或跳过、验证失败分支不会产生半提交。交付说明写明该流程为什么不做二次运行。

**文件类产物验收**：下载/导出类流程不能以「保存按钮已点击」或「对话框已关闭」判定成功。必须检查目标路径确实新增文件、文件头与类型匹配（如 PDF 的 `%PDF-`）、大小非零，并在条件允许时解析内容核对关键业务字段；交付记录文件大小与摘要。**内容核对不是可选项**：当列表里有多条相似记录时，"文件名对了但内容是另一条记录"是最常见的静默错误，只查文件名会把第一个文件复制成两份。

**系统另存为对话框**：不要靠左侧导航栏逐级点击目录。直接往文件名输入框（`AutomationId=1001`）写**完整绝对路径**，Windows 会解析路径并定位到目标目录，再点保存（`AutomationId=1`）。这样一次输入同时指定了目录和文件名，避免"记住上次目录导致存到别处"。同名文件已存在时会再弹一个 `#32770`「确认另存为」，按 `是(Y)` 覆盖；这个二次确认也必须用同样的浮层检测发现，不能当作主对话框的一部分。

**隐私与留证**：GUI 证据截图和 OCR 结果可能含审批编号、金额、账号、姓名等个人信息。只保存必要证据，交付前清理临时截图/JSON，不把真实业务数据写入可复用脚本或技能示例；示例一律使用占位值。**调试期的真实编号、客户名、金额、账号、绝对路径不得进入任何会被提交的文件**——plan 文件、SKILL.md、脚本注释、测试用例都算。运行时用 `--set` 传真实值，文件里只留 `${var}` 和形如 `YYYY-MM-DD`、`<某绝对目录>` 的占位说明。定位已校准这一事实要写清楚，但校准用的具体业务值不能留下。

## Hard Rules

- **短探测优先，全流程只做验收**：调试期每个验证控制在秒级、只回答一个问题、尽量不改变界面状态；确认一段再跑下一段。把一次全流程当成调试手段，会同时浪费时间和状态，还让失败原因变得无法归因
- **先看屏幕，再动手**：每次开始动作循环前、改动脚本后、以及任何失败之后，先跑一次 `scene.py` 拿到完整场景（显示器与缩放、前台归属、窗口尺寸、遮挡、对话框、浮层），再读一次页面内容。元素列表和状态摘要都是推论，场景本身才是事实。拿着旧假设继续操作是本技能最常见也最贵的错误——它不会报错，只会点点错地方或者点了没反应
- **优先语义定位，坐标兜底**：UIA/Playwright 定位器能用就不用坐标
- **坐标必须来自观察，但不必每次动作都重新观察**：坐标只有两个合法来源——本次运行的语义定位结果，或上次运行记录并当场校验通过的缓存。禁止的是凭空写死的常量。缓存坐标的合法条件是：存的是客户区相对比例、带像素指纹、点击前校验通过；三者缺一就当它不存在，退回语义定位。「每次动作都全屏重找」和「写死像素」是两个极端，都不对
- **输入按表头名映射**：不假设列顺序
- **动作函数单一职责**
- **凭据不进版本库**：`.env` 必须进 `.gitignore`，交付前 `git check-ignore .env` 验证

## Gotchas

| What happened | Rule |
|---|---|
| `send_keys` 输入没进编辑框 | 窗口未聚焦；先 `set_focus()` 再点击目标控件 |
| 粘贴后内容没变 | 自绘编辑器要先点击获得焦点，Ctrl+A/Ctrl+V 之间留 100ms |
| 应用已打开但连不上 | 先恢复并重新观察窗口，再重建元素定位；Windows 可用 `findwindows.find_elements(..., visible_only=False)` 辅助发现，不把它当作恢复最小化窗口的替代品 |
| Qt 应用语义树只有容器 | 先扩大深度检查完整后代和内嵌网页/CEF 区域；目标确未暴露时才用容器内 OCR/截图定位，不把 Qt 等同于无 Accessibility。若 CEF 只暴露 `Chrome Legacy Window`、无行级节点且点击不改变状态，标记 `embedded-web-no-bridge`，交付说明要求页面级桥接/浏览器自动化或人工接管，不把坐标脚本标记为已验收 |
| Qt 下拉框 / 对话框点不到 | `QComboBox` 弹出的下拉列表、`QMessageBox`/`QDialog` 都是**独立顶层窗口**，不在主窗口句柄内。按 `class_name_re="Qt[56]QWindowIcon"`（Qt 5.x 为 `Qt5QWindowIcon`，6.x 为 `Qt6QWindowIcon`，用 Accessibility Insights 核实）枚举同级窗口后再定位；只给主窗口截图永远看不到它们 |
| Qt 表格读不到行 | `QTableWidget`/`QTableView` 用 UIA 的表格模式按 `(row, column)` 取单元格，不要按文本在整个窗口里搜——同名单元格会有多个匹配 |
| Qt 输入框点不进去 | 表单里的输入框常不暴露为 UIA `Edit`（自绘），按 "找 Edit 控件" 的思路会一无所获。改用占位符文本定位：OCR 找到该字段的 label 或 placeholder，点它**右边界往右一段距离**的位置（输入框通常在 label 右侧），再粘贴输入 |
| 截图出现其他应用 | 立即丢弃该证据并禁止点击；截图前激活目标、断言前台句柄，再捕获目标窗口。仅按屏幕矩形抓图会受遮挡影响，不能当成目标窗口证据 |
| 窗口截图底部是黑的 | PrintWindow 对 GPU 合成的 Qt/CEF 窗口、或窗口底部超出屏幕时，只返回可见部分，其余是纯黑。必须检测「底部连续整行全黑」并回退到屏幕裁剪；否则 OCR 看不到下半屏，定位会莫名其妙失败 |
| 点了下载什么也没发生 | 对话框可能已弹在另一个进程里（下载组件托管）。按 `GW_OWNER` 跨进程枚举，并对动作前后的浮层句柄做差集；不要只观察主窗口就断定"没反应" |
| Playwright 定位器偶尔失败 | 使用 Locator 自动等待和具体状态的显式等待；DOMContentLoaded 不代表动态业务元素已加载 |
| 批量邮件发到一半被限流 | 加大间隔；个人 SMTP 有日限额 |
| 钉钉 webhook 返回 310000 | 关键词或加签校验失败；更多应用特例见 `references/app-notes.md` |
| 写 Excel 后列宽全是 `#####` | 写完必须 `auto-fit-columns`；格式码用 US notation（`,` 分组 `.` 小数，Excel 自动本地化） |
| 脚本跑完 Excel 文件还被锁 | `xlwings` 写完必须 `close + save`；WPS COM 路径同样 `Close(SaveChanges:=True)`；不关会留进程锁文件 |
| 点了按钮应用没反应 | 先重新观察并断言状态变化，不要凭直觉补点击；只有在显式等待无法观测到任何中间态时，才在动作后加一次固定延时，并在代码里注释原因 |
| 关闭标签/窗口时卡住 | 弹了确认框（保存API/未保存更改）；默认保留现场并报错，只有本次脚本新建且确认不含用户输入的临时文档才能选择「不保存/Discard」 |
