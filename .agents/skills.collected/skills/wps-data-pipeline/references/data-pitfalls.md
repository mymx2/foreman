# 数据质量问题（实测，量化到条数）

标签只有四类，写成 `来源·结论`：

| 标签 | 含义 | 引用前必须确认 |
|---|---|---|
| `实测·可用` | 本机跑通过或已复现可用 | 能指向可执行复验命令，或指向本文件带复验命令的表行 |
| `实测·不可用` | 本机复现过失败 | 同上；拿不出复验方式的降级为 `推断` |
| `文档·未测` | 官方文档或上游参考实现里有，本机未跑 | 注明文档/代码位置；改关键路径前先小范围试一次 |
| `推断` | 无文档依据，靠机制推理 | 不得作为交付依据 |

「实测」不是修辞：凡出现处都要能指向一条可执行复验命令；**脚本未暴露入口的 action 例外**，须在该行注明「脚本无入口」。

**范围声明**：以下条数取自「在库表」工作簿，换文件后只作量级参考；该工作簿的完整名录、逐表条数与逐表复算命令在 `rbz-inventory.md`，本文不重复。

这份表的列格式是给人看的，不是给程序读的。下面的数字来自一次真实取数，作用是让后人**不用重走一遍就能判断自己的统计口径有没有跑偏**。

数字只覆盖已逐表统计过的部分，未逐表统计的项不编造。**分母不可用**：空值只统计了五张表，而 float 是另一套统计范围，两者分母不同；再加上第 1、2 节的问题会在同一行上重叠（同一行可能既有出库时间问题、又有库位号问题），所以**不能把各分项直接相加去凑总行数**。

## 1. 出库时间列：一列里混着四种东西

| 形态 | 条数 | 说明 |
|---|---|---|
| `datetime.date` | 约 176,000（`推断`，只作量级） | 真正的日期。占比不可算，理由见下 |
| `float` 形如 `20211216.0` | 合计 7,087（分表计数见 `rbz-inventory.md`） | 单元格被设成日期格式，存的却是 8 位整数 |
| 文本 `特惠` / `禁售` | 未逐表计数 | 业务状态标记，混在日期列里 |
| 空值 | 合计 16,926（分表计数见 `rbz-inventory.md`） | 五张表合计；其余表未统计 |

**这四行不是互斥分区，不能相加，也不能拿总行数当分母。** 有两张表根本没有「出库时间」列（表名与算式见 `rbz-inventory.md` 工作表清单），扣掉它们之后，有该列的数据行上限是 191,397。三个已统计桶相加是 `176,000 + 7,087 + 16,926 = 200,013`，比上限多 8,616。差额说明三个桶不是同一口径下的互斥分区：176,000 若按全簿日期格计、空值只按五张表计，两者分母不同；多出的 8,616 无法用覆盖不全解释，待按同一口径重算后再引用。标签 `推断`——原先的占比结论不可靠，已删除。可信的只有量级：日期形态约 17.6 万，两类异常分别在万级和千级。

### 影响

- **openpyxl 会整本失败**，不是某一行失败：它读到「日期格式 + 值 20211216」时抛 `serial value outside the limits for dates`（Excel 日期序列上限 2,958,465，20211216 远超）。这是本技能坚持用 python-calamine 的唯一原因。
- **不归一化就丢行**：把 `20211216.0` 当非日期丢弃，等于凭空少 7,087 行；按月/按日分组时这部分会整体消失，而且不会报错。
- **空值不能当 0**：空是「未填」，0 是「当天出库 0」。当 0 会把均值拉低，删掉会把均值抬高。正确做法是给分母：`均值 = 有值行合计 / 有值行数`，并同时报告空值条数。
- **`特惠`/`禁售` 不是脏数据**：它们是业务状态。计行数时保留，进日期统计时排除，并单列一张「非日期取值」统计表。当成异常清洗掉，等于静默改变业务口径。
- **肉眼看不出来**：`20211216` 在日期格式的单元格里就显示成一个数字，看起来像「某列数值有点怪」，只有读类型才会发现整列是混合的。

### 归一化口径（全流程必须一致）

1. `date` / `datetime` → `YYYY-MM-DD`
2. 8 位整数或整数型浮点 → 先校验落在 `19000101`–`29991231` 且月日合法，通过则转 `YYYY-MM-DD`；不通过保留为数值（避免把恰好 8 位的数量误判成日期）
3. 文本 → 尝试 `YYYY-MM-DD`、`YYYY/M/D`、`YYYY.M.D`、`YYYY年M月D日`、带时分秒的变体，能解析则转 ISO
4. 文本解析不了（`特惠`/`禁售`）→ 原样保留，类型记 `text`
5. 空值 → 类型记 `empty`，**不进任何算术**

### 复算口径没跑偏

拿同一份文件跑，先看名录再按表查（命令在**用户工作目录**执行，脚本用绝对路径 `"$SKILL/scripts/parse_workbook.py"`，`$SKILL` 指技能安装目录）：

```bash
python "$SKILL/scripts/parse_workbook.py" 导出.xlsx --list
python "$SKILL/scripts/parse_workbook.py" 导出.xlsx --sheet <表名> --where "出库时间=空"
```

各表的期望命中数在 `rbz-inventory.md`。数据会随快照变，但**量级和比例不该跳变**；差一个数量级说明表头行选错或列名对不上，不要继续往下算。

想看原始形态（而不是归一化后的值）加 `--raw`：同一列会同时出现 `2021-12-16 00:00:00`、`20211216.0`、`特惠`、空串四种写法。`--raw` 只影响导出，不影响 `--fingerprint`。

## 2. 库位号列：库位编码里混着形制描述

| 形态 | 例子 | 性质 |
|---|---|---|
| 真实库位编码 | 数字分段形式 | 可 JOIN 库位主数据 |
| 形制/形制-位置描述 | `杂`、`杂框`、`1手卷`、`1里卷`、`1册页` | **不是库位**，是「这本书/这件货长什么样、放在哪一类位置」 |

### 影响

- 按库位号分组做 TOP-N 或占比时，会凭空多出「杂」「杂框」这类伪库位，挤占真实库位的排名。
- 拿这列 JOIN 库位主数据会大面积 unmatched；如果按「匹配不上的就丢掉」处理，等于静默删掉一批真实出库行。
- 只按字符串长度或首字符过滤会把 `1手卷` 当成 `1-…` 一类的库位，误伤更难发现。

### 处理

1. 先用白名单正则识别真实库位编码格式（例如分段的纯数字），命中的归「库位」。
2. 未命中的**不删**：新加一列 `库位形态`，把 `杂` `杂框` `1手卷` `1里卷` `1册页` 等归类进去。
3. 库位维度统计只跑「库位」那一组，同时在报告里说明有 N 行属于形制描述、未纳入库位维度。这样占比的分母是透明的。

## 4. 表结构与表名不稳定

表数与规模只是某一次快照的现状。表会被改名、增删、拆分——当前名录与各表行列数只记在一处，见 `rbz-inventory.md`，本文不重复。

- 不要把表名和列名写进脚本常量；每次先 `--list`，再按名字取。
- 括号里的中文可能是渠道别名，不一定是表名——以 `--list` 实际输出为准。
- 跨表汇总前先确认每张表的表头是否同构（列名、列序都可能不同）；按**列名**映射，不要按列序号。

## 5. 快照边界

- 每次取数都记下：来源（接口下载 / 人工下载）、文件名、字节数、下载时刻、`--list` 的合计行数。没有这些，两次结果不一致时无法判断是数据变了还是取错了文件。
- 人工下载没有 `fize` 可校验，完整性只能靠 `PK\x03\x04` + 行列数是否合理 + 抽查几条记录。
- 比对两次快照用 `--fingerprint`：哈希在归一化之后计算，所以「只改了单元格格式」不会产生差异，产生差异的一定是值或行数。

## 6. 两次快照怎么比

脚本不提供比对子命令——差异语义没有唯一正确解释，硬编码只会固化一个会漂移的口径。需要时用下面这段（只读、无依赖）：

```python
import json, sys
from collections import Counter

a = {s["name"]: s for s in json.load(open(sys.argv[1], encoding="utf-8"))["sheets"]}
b = {s["name"]: s for s in json.load(open(sys.argv[2], encoding="utf-8"))["sheets"]}
for name in sorted(set(a) | set(b)):
    if name not in b:  print(f"{name}\t整表消失 {a[name]['rows']} 行"); continue
    if name not in a:  print(f"{name}\t整表新增 {b[name]['rows']} 行"); continue
    ca, cb = Counter(a[name]["row_hashes"]), Counter(b[name]["row_hashes"])
    print(f"{name}\t{a[name]['rows']}→{b[name]['rows']}"
          f"\t消失 {sum((ca-cb).values())}\t新增 {sum((cb-ca).values())}"
          f"\t相同 {sum((ca&cb).values())}")
```

判读要点：

- 「消失 + 新增」就是真实变更量；「相同」+「消失」应等于旧行数，对不上说明两次快照被不同口径处理过。
- 指纹基于归一化值，只改格式不会产生差异，`--raw` 也不参与计算（它对 `--fingerprint` 本来就无效）——拿「一次用 `--raw` 一次没有」解释快照差异是条死路。真的整表全变，只能是口径或表结构变了。
- 顺序不参与比较。插行、排序都会改变行序，但不会产生消失/新增。
- 整表「全变」通常不是业务变更，而是两次快照来自不同表结构或不同归一化版本。
