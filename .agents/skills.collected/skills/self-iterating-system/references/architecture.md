# 五层架构契约

自迭代 Agent 系统的分层结构。每层职责用"只 X 不 Y"定义；层间通过可信上下文流转，不依赖人工搬运。契约与行业无关：文中"产品"可替换为游戏、内容、活动、功能模块等任何可被生产与运营的对象。

## L1 数据感知层 — 看见发生了什么

职责：把前一天的数据、变更记录和代码整理成可信上下文。只感知，不分析。

输入：业务多级报表（渠道/产品/内容三级或业务自有层级）、实验快照、变更记录、版本时间线、产品代码与配置。

输出（进入全局状态）：

- 每日数据包：T+1 出数，分级报表 + 实验快照。数据口径只有一处定义，AI 与人看的是同一份数。
- 归因双轨：迭代记录（我们改了什么）× 变更日志（环境变了什么）。指标涨跌先分清是自己的改动还是外部动作。
- 代码级上下文：可直接读产品源码与配置。内容/配置是「算法 + 参数 + 随机种子」的确定性产物时，提案能精确到改哪个参数。

门禁（整批验收）：核心报表构建失败，当天所有任务中止。宁可不跑，也不让错误数据生成结论。

## L2 运营决策层 — 只分析，不执行

职责：判断当天最值得改哪款产品，产出带预期的待评审方案。

组织模式：主持人 + 专家团的对抗模式。运营分析没有标准答案，单 Agent 容易把方案做得过于简单、把原因归到无法行动的客观因素上、或给出缺少证据的结论。

- 主持人：全局收敛。识别任务类型 → 强制加载任务手册（步骤/门禁/已知死路）→ 按需召唤专家 → 收敛结论 → 写成待评审提案。只有主持人有写权限，专家全程只读。
- 专家团：每个专家先独立看数，形成自己的上下文和证据链，避免过早锚定。专家之间围绕具体方案互相论证，分歧在对话中解决，最后由主持人收敛——不把未经处理的争论直接抛给用户。

标准专家角色（按业务替换第三行为领域专家）：

| 角色 | 职责 | 关注目标 |
| ---- | ---- | ---- |
| 数据分析师 | 分析数据 + 迭代日志 + 业务背景，定位异常并归因，提可执行提案 | 迭代目标：核心指标提升 |
| 开发工程师 | 读策划方案、真实代码与配置，决策可行性：接受/修正/驳回 | 可落地、风险可控、成本合理 |
| 领域设计师 | 结合数据分析结论提出 1–3 个候选，产出终选提案书 | 体验差异化、多方共赢 |
| 评审 | 独立看数，质询与反驳，以唯一核心指标作为准则 | 有效性、准确性、目标对齐 |

产出两类结果：现有产品迭代提案、新产品立项书。两者都必须是可证伪交付物。

### 迭代提案的分析动线

现状取数（漏斗与核心指标，横向拉同类型产品对照）→ 问题定位（卡在哪一级，该加引导还是该降门槛）→ 读真实配置（与同类产品配置对照）→ 读真实代码（不能跳，确认要改的模块真实存在、现状怎么实现）→ 数据分析 × 开发联合结论（带代码证据的方案方向）→ 提案文档三段式：数据现状 / 归因分析 / 提案清单，条目细到「改哪个文件、怎么改、目标值多少」，每条按「改的是什么层」标注落地通道与验证方式：配置直调（免发版，护栏内小步快调，次日自动复盘）、内容参数调整（走生产迭代 + 可视化验收）、机制调整（走生产迭代 + 实验上线，预注册预期）。

### 新立项的对抗流程

门禁：先锁定核心指标方向，并先读「已知死路清单」，防止重跑白工。阶段一 并行深潜：数据分析师产出立项约束清单（目标人群规模、必须满足与避开的特征、同门槛产品的量化基准），评审产出死路清单 + 口径审计；两份报告齐了才允许开始想方案。阶段二 设计对抗：领域设计师产出 2–3 个候选，每个必答品类对比、一句话核心循环、机制好在哪、与现有产品的差异、双赢设计；数据分析师主动挑战设计假设——这一轮对抗是方案粒度的唯一来源。阶段三 主持人收敛：多候选收敛为单推荐，被淘汰方向只留一句话附注。阶段四 评审终审质询：是否落回已知死路、证据是否被污染、与现有产品的查重论证是否成立。产出：立项书（名称 + 简述 + 数据分析）+ 预注册预期，进待人工评审。

### 专家团协作节奏

阶段一 无交流各自看数：数据分析师跑一遍数据 + 分析 + 建议全流程，开发读代码理解已有逻辑与「当初为什么这么写」，评审独立看数先出死路清单与口径审计。阶段二 讨论交流：数据分析 × 开发对着代码与数据讨论，分歧不许上报主持人，必须自己讨论出联合结论；再交给评审对抗质询，对照核心指标逐条反驳。阶段三 循环迭代（默认多轮）：按质询结果补证据 / 修方案，被说服就明确认账，不许硬撑。最终产出：待人工评审的提案。

## L3 生产执行层 — 只执行，不分析

职责：接收已确认方案，完成策划、素材、代码和内容生产。

调度中枢统一调度：不生产任何内容，只理解需求、规划链路、调度 Agent。所有路由决策由调度中枢通过 Structured Output 统一做出，避免判断散落在各条边逻辑里。用户中途修改需求时，调度中枢判断影响范围，逐级路由到需要重做的下游环节，而非全链路推倒重来。

调度中枢的五项职责：

1. 任务规划：基于项目阶段和用户意图，决定下一步调度哪个 Agent。
2. 会话记忆：感知全局对话历史，理解上下文。
3. 状态管理：追踪各 Agent 产出进度（已产出 / 已审核 / 已确认）。
4. 意图识别：区分用户是在推进流程、修改方案还是提问咨询。
5. Agent 编排：为目标 Agent 生成精准的工作指令，而非泛泛描述。

标准生产链路（按阶段推进，角色按业务改名）：

1. **调研 Agent**：从发散到收敛。不要求用户用文字精确描述想要什么，先给出真实候选样例让用户指方向，再分析选中样例提取核心特征作为搜索关键词定位详细资料，同时筛出 2–3 个风格参考贯穿后续素材生成流程。
2. **策划 Agent**：产出信息密度优先的设计文档。每段描述必须能被下游直接消费：实体定义给开发写类、操作规则给开发写逻辑、资产清单给素材生成、内容设计定配置结构。一段描述不能映射到具体开发动作就不写。策划阶段先定整体风格与基调，作为全局约束。
3. **素材 Agent（视觉/音频/文案）**：生产线式生成，不是"一个 prompt 一份素材"。设计文档解析需求清单 → 依赖分析定生成顺序 → 分组并发 + 三级一致性锚点（基准风格参考 → 首份生成素材作锚 → 多状态对象的标准态参考）→ 合成整体框架图 → 多模态分析布局输出结构化描述给开发。支持四种执行模式：首次全量、局部重生、续生失败资产、素材咨询，由意图分类路由。
4. **开发 Agent**：在远程隔离容器中执行，读写文件、装依赖、起开发服务器。设计产物通过全局状态自动流入系统提示词，无需额外交接环节。
5. **内容设计 Agent**：设计内容工厂而非逐份内容。定义数据结构、生成算法、验证策略和递变曲线，方案严格限定五章（类型、数据结构、生产方式、验证方式、递变曲线——各领域实例化时改名，如游戏域：类型→gameType、递变曲线→难度曲线，由 agentic-game-dev 技能承载），优先基于开发 Agent 已实现的接口设计，产出即可落地。
6. **内容实现 Agent**：生成 → 验证 → 重试，零运营成本。

内容生成模式选择两问：生成后是否必然有效（满足约束、可用、合规）？有效性判定是否耗时？据此选"生成即验证"或"离线预生成 + 验证"。有效性本身无法自动判定的内容（如依赖人工审美的叙事类）走第三条路：人工抽检 + 发布后数据回收。确定性生成带来三项迭代能力：可溯源（任意一份可用种子 + 参数精确复现）、可改造（提案明确到参数及目标值，改完用种子逐份 diff 回归）、可验收（预览与运行时复用同一条生成链路）。

Human-in-the-loop 只在三类节点暂停：方向选择（调研选样例）、方案确认（策划/内容/素材产出 Review）、质量验收（代码完成后预览）。其余全自动推进。

## L4 工程基建层 — 让 Agent 只写差异化逻辑

职责：分层容器架构 + 固化层/可变层壳应用。没有宿主与容器环境的业务（独立 App、纯后端服务），本层简化为"通用能力库 + 产品接入层"：同样划分固化与可变，只是承载从壳应用变成代码库，复用原则不变。

- 容器分层：调度层做流程编排与多 Agent 协调；容器服务层管环境与依赖；Agent 层在真实工作区读写代码、跑命令。每个执行节点对接一个独立远程容器，预装对应壳应用。
- 壳应用固化层：工程脚手架、分层架构、通用 UI 框架、状态管理、通用接口（配置查询推进、权益管理、商业化打通）、资源加载链路和事件总线。服务端通用能力完全复用，新产品接入无需重复开发。
- 可变层：业务对象与管理器、主场景逻辑、具体 UI 与交互、内容配置、权益效果、资源定义。Agent 只写这些。

宿主与产品通信协议（以模块联邦类动态加载为例）：

1. 统一数据查询通道：一个通用异步函数承载所有数据请求，产品侧不关心数据来源。
2. 标准生命周期回调：产品在关键节点单向通知宿主，模板统一封装。
3. 双向事件协议：上行（产品 → 宿主）与下行（宿主 → 产品）两条固定通道承载所有自定义业务事件。

## L5 治理与自进化层 — 能用工程链路，就不依赖提示词

职责：设置门禁、沉淀知识、回收实验结果、治理记忆。

- 硬门禁：核心指标与纪律写进代码约束，AI 结构上改不了；方案落地收归人工核检。
- 知识库：分事实/判断/打法三层，结论按证据强度分级，未验证的只能当假设。
- 可证伪的下注：提案 / 立项时预注册预期（预测区间、引用了哪几条既有知识、证伪条件；评审的反对意见随预期一起入库）→ 人工确认后以实验发布上线 → 版本时间线（版本变更 / 实验起止 / 全量 / 回滚）→ 到期自动结算，先对「实际交付了什么」再对照预期取数 → 分层归因按序判定（命中即停）：执行错（实际交付与方案不符，或口径 / 取数写错 → 本次验证作废，补避坑条目）；方法错（交付符合方案但度量方式混杂，干预外因素未隔离 → 结论退回未验证）；假设错（度量干净，但结果与预期相反或落在预注册预测区间之外 → 该规律标记已推翻）。所有知识库修改落待评审，评审通过后转正。
- 交付看板：产品方案与数据结果给业务/AI 产出，技术实现看板给开发，实验数据回流进入下一轮。

无人值守门禁：

1. 数据整批验收：核心报表失败当天中止。持续无报表说明 L1 未就绪，应回 L1 补数据通道而非每天中止。
2. 验收真实状态：不信"做完了"，逐项核对交付物——立项书是否新建、提案是否更新、待结算清单是否清空。检查方式逐条写明（查文件 / 查 API / 查队列），未通过在同一会话催促续跑，预算（轮次 / 时长 / token 上限，设计时显式选定）耗尽才标记失败交人工。
3. 自动巡检：定时回收假死任务（超过阈值无心跳或超时长未完成即判定假死，阈值设计时定）、补跑漏批、纠正"看起来完成实际没有交付物"的状态。
4. 统一交付标准：自动化只省掉中途等待同意的步骤，产物进待评审队列，评审权在人。
