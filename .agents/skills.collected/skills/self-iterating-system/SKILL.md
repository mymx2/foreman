# Self-Iterating System

判断与执行分离；交付的不是结论，是可证伪的下注。

搭建一套能在真实数据反馈下自己变好的 Multi-Agent 系统，而不是跑得更多的自动化流水线。

## Overview

本技能把一套自迭代 Agent 方法论操作化为可执行的设计与诊断流程。核心架构：人定义唯一核心指标与行动边界并审核关键方案；AI 负责策略、开发与数据归因。运营 Agent（判断）与生产 Agent（执行）分离，二者职责隔离但可互相查阅上下文。方法论与行业无关：把"产品"换成游戏、内容、活动、功能模块，结构同样成立。

## Outcome Contract

- Outcome: 用户得到一份可落地的自迭代 Agent 系统设计（五层架构 + 双闭环 + 记忆治理），或对现有系统的诊断报告与修复清单。
- Done when: 设计覆盖五层职责划分、两个闭环的流转契约、Human-in-the-loop 介入点、可证伪交付物格式、四层记忆结构；或诊断定位到具体缺失环节并给出修复优先级。
- Evidence: 架构分层图（文字版）、各层输入输出契约、门禁清单、记忆元数据 schema、预期-真实对账表样例。
- Output: 设计方案 Markdown 或诊断报告，含每条设计决策的理由。
- Authorization: 只做设计与诊断，不直接改用户代码库；涉及具体实现时给出接口契约而非完整代码，除非用户明确要求实现。

## When to Use

- 从零设计覆盖"生产 + 运营"全链路的 Agent 系统。
- 现有 Agent 系统单点都提效了但整体业务没提速（能力孤岛）。
- Agent 持续产出方案但质量不随运行次数提升（缺自进化机制）。
- 多 Agent 之间上下文靠人工搬运、需求中途变更不知影响范围。
- 无人值守任务把错误结果写进了下游系统（缺门禁）。

Not for: 单次内容生成、无数据回流的纯 Workflow、传统软件架构设计。

## Process

1. **定核心指标与边界。** 与人确认三件套：核心指标（全系统唯一、可衡量，所有方案以它为最终裁判；多产品线各定子指标时必须显式声明汇总规则，如"子指标加权后服从全系统指标"。汇总可行性判据：子指标量纲可比、资源分配可仲裁即汇总为一套系统；量纲不可比或目标互斥则分系统各自闭环，五层与记忆作用域各画一份）、行动边界（AI 不可逾越的红线，每条必须能写成 `if 条件 then 拒绝` 的机器规则——"禁止泄露用户数据"是口号，"出库前校验字段白名单，含 PII 字段则拒绝"才是边界）、人保留的审核点。指标变更必须走显式流程：标记依赖旧指标的历史知识全部转候选，重对账后再生效。产出物：一页纸的「指标 + 边界 + 审核点」清单。完成标准：每条边界都写出了对应的检查规则（lint、SQL 校验或运行时钩子均可）。
2. **拆判断与执行。** 把系统拆成运营 Agent（看数、归因、定优先级、产出带预期的提案，只分析不执行）与生产 Agent（接已确认方案，完成策划、素材、代码、内容生产，只执行不分析）。二者上下文隔离但可互相查阅。完成标准：每个 Agent 的职责能用"只 X 不 Y"一句话说清。
3. **画五层架构。** 按 L1 数据感知层 → L2 运营决策层 → L3 生产执行层 → L4 工程基建层 → L5 治理与自进化层 组织。加载 `references/architecture.md` 获取每层的职责、输入输出契约与门禁设计。每层用填空模板落定：`来源：___；产出：___；失败时中止条件：当 ___ 时`。没有实验平台时，用"灰度发布 + 前后对照 + 预注册预期"替代 AB 实验，结算逻辑不变。完成标准：五层模板全部填完，无空项。
4. **设计双闭环。** 生产闭环解决上下文流转：调研报告、策划方案、资产清单、内容/数据结构进入全局状态，下游直接读取；需求中途变更由调度中枢统一判断影响范围并路由重做到对应下游。迭代闭环处理数据驱动决策：感知状态 → 理解目标 → 拆解决策 → 调用能力 → 产出方案 → 读取反馈 → 沉淀经验。完成标准：两个闭环的每一环都有明确的产出物和下一环的触发条件。
5. **设计生产链路。** 以调度中枢为唯一路由点（Structured Output 统一决策，不把判断散落在各条边逻辑里），专业 Agent 按阶段推进：调研 → 策划 → 素材 → 开发 → 内容配置 → 配置实现。流程骨架用 Workflow 引擎硬保证（流转、审核、暂停恢复不依赖模型判断），节点内部给模型充分自主推理空间。Human-in-the-loop 只在三类节点暂停：方向选择、方案确认、质量验收。完成标准：链路图标注每个节点的输入（来自全局状态的哪部分）、输出（写回全局状态的哪部分）、审核点。
6. **设计可证伪交付物。** 每个运营提案必须写明：预测指标区间、引用了哪些知识、什么结果会证伪当前判断；评审的反对意见随预期一起入库。加载 `references/templates.md` 获取填好的交付物、提案、立项书示例。实验到期后逐条对账预期与实际，并按序分层归因（命中即停）：执行错（实际交付与方案不符，或口径/取数写错 → 本次验证作废，补避坑条目）；方法错（交付符合方案但度量方式混杂，干预外因素未隔离 → 结论退回未验证）；假设错（度量干净、交付符合，但结果与预期相反或落在预注册预测区间之外 → 该规律标记已推翻）。完成标准：交付物三个必填字段齐全且能对账，对账结论落到执行/方法/假设三类之一。
7. **设计四层记忆。** 核心规则（核心指标、边界、口径红线，常驻注入）；知识（已验证规律，按现象/机制/未验证推断分级，按作用域和匹配分动态检索）；历史记忆（原始事件与 LLM 提炼摘要，原始事件是唯一可直接引用的历史证据）；会话记忆（中断重连用）。记忆正文只保留"结论 + 判断依据"，带治理元数据：作用域、来源证据、证据等级、置信度状态、版本链。加载 `references/memory-system.md` 获取完整 schema、冲突优先级与级联失效规则，加载 `references/templates.md` 获取填好的记忆条目示例。完成标准：每条记忆可回溯到生成它时的系统状态。
8. **加无人值守门禁。** 数据整批验收（核心报表构建失败当天全部中止，宁可不跑也不让错误数据生成结论；持续无报表则说明 L1 未就绪，回第 3 步补数据通道而不是每天中止）；验收真实状态（不信"做完了"，逐项核对交付物存在：立项书是否新建、提案是否更新、待结算清单是否清空，检查方式可以是查文件、查 API 或查队列，逐条写明）；定时巡检（回收假死任务——超过阈值无心跳或超时长未完成即判定假死，补跑漏批，纠正"看起来完成"的状态；预算指轮次/时长/token 上限，设计时显式选定）；统一交付标准（产物进待评审队列，评审权始终在人）。完成标准：每道门禁写明检查方式和失败后的处置路径。
9. **验证设计。** 对照 Red Flags 逐条自查；确认存在的风险项连同缓解措施写入方案的「风险与权衡」章节；给用户输出设计方案或诊断报告。完成标准：每条设计决策都附带它解决的具体痛点，Red Flags 自查结果全部有去向（修复或记录为已接受风险）。

## 诊断模式（现有系统）

当用户带着现有 Agent 系统来问"为什么不行"时，按以下顺序排查，命中即定位：

1. 各环节都快但整体慢 → 能力孤岛，缺上下文流转（回 Process 第 4 步）。
2. 方案越产越多但没变好 → 交付物不可证伪、缺预期-真实对账（回第 6 步）。
3. 不同人/不同次运行归因结论打架 → 经验没沉淀为分级知识（回第 7 步）。
4. 错误结果进了下游 → 缺数据验收门禁（回第 8 步）。
5. 流程偶尔失控 → 骨架交给了模型判断，改 Workflow 硬保证（回第 5 步）。
6. 用户被过度打断或全程无感 → Human-in-the-loop 介入点错配（回第 5 步）。

## Common Rationalizations

- "做一个超级 Agent 包揽所有能力" — 判断和执行混在一起，归因、优先级、生产互相污染；拆开才能各自沉淀上下文。
- "每一步都让人确认更安全" — 过度打断等于人工流水线；只在方向选择、方案确认、质量验收三类节点暂停。
- "会话正常退出就是任务完成" — 无人值守必须验收真实交付物状态，否则错误结果静默进入待评审队列和知识库。
- "经验都写进知识库就会变好" — 不分证据等级、不带证伪条件的知识是噪声；低等级内容禁止使用强断言。
- "内容让 AI 直接生成每一份" — 定义生成算法 + 参数 + 随机种子的确定性产物，才可溯源、可改造、可验收。

## Red Flags

- 路由决策散落在各 Agent 的边逻辑里，而不是调度中枢统一 Structured Output。
- 设计类 Agent 和执行类 Agent 共用一套执行环境（前者直接调 LLM API 即可，后者才需要隔离容器与完整工具链）。
- 素材资产没有一致性锚点机制，逐份独立 prompt 生成。
- 记忆正文保存一次性细节和时效数值，而不是"结论 + 判断依据"。
- 方案审核权交给了 AI 自动放行。
- 用"显著""必然"等强断言描述现象级证据。

## Verification

1. 设计方案五层齐全，每层职责一句话可说清（只 X 不 Y）。
2. 双闭环每一环有产出物和触发条件；逐环核对清单确认无断点（断点 = 某环缺产出物或缺触发条件）。
3. 交付物模板含预测区间、引用知识、证伪条件三字段。
4. 每条记忆带五个治理元数据字段。
5. 门禁清单每条有检查方式和失败处置。

## 环境前提与降级

设计前先确认用户环境，缺什么就走对应降级：

| 前提 | 缺失时的降级 |
| ---- | ---- |
| 报表/数据平台 | L1 从日志、数据库直查或人工导出起步，先跑半自动（人触发、AI 分析），数据通道就绪后再无人值守 |
| 实验平台 | 用灰度发布 + 前后对照 + 预注册预期替代 AB 实验；结算与归因逻辑不变，证据等级上限降为"现象" |
| 版本时间线 | 用 git tag / 发布记录 + 变更日志手工维护 |
| 宿主/容器环境 | L4 简化为"通用能力库 + 产品接入层"；Coder 类 Agent 在普通工作区执行，隔离要求降为目录级 |
| 工单/队列系统 | 用 git 目录 + frontmatter 状态字段作待评审队列（`status: pending/approved/rejected`），门禁检查改为读目录与状态字段 |

## Hard Rules

- **人保留两项职责不可让渡**：定义唯一核心指标与行动边界、审核关键方案。其余全部交给 AI 在边界内闭环。
- **生产 Agent 只接收已确认方案**，不接受模糊需求；模糊需求先在调研环节收敛（让用户从真实候选样例中指方向，多模态分析提取特征）。
- **所有自动化产物进待评审队列**，评审权在人；自动化只省掉中途等待同意的步骤，查重、读代码、证据要求与交互式流程一致。
- **宁可不跑，不用错误数据跑**：核心报表构建失败，当天所有任务中止。

## Gotchas

| What happened | Rule |
| ------------- | ---- |
| 运营 Agent 直接改了线上配置 | 运营层只分析不执行，产出待评审提案；执行必须过人工审核后走生产层 |
| 提案只写"建议提升转化" | 提案条目必须细到「改哪个文件、怎么改、目标值多少」，并按改动层级标注落地通道（配置直调 / 参数迭代 / 机制实验） |
| 中途改需求全链路推倒重来 | 调度中枢判断影响范围，只路由到受影响的下游环节重做 |
| 内容生成后发现有无解/不可用个案 | 生成模式先回答两问：生成后是否必然有效、有效性判定是否耗时；再选"生成即验证"或"离线预生成 + 验证"。有效性无法自动判定的内容走"人工抽检 + 发布后回收"第三条路 |
| 多 Agent 互相引用过期上下文 | 全局状态单一事实源，下游只读状态不靠人工搬运；历史证据只引用原始事件，摘要仅作背景补充 |
| 新产品接入重写服务端 | 壳应用固化层预置通用能力（配置查询推进、道具/权益、商业化打通），Agent 只写可变层差异化逻辑。没有宿主场景时，L4 简化为"通用能力库 + 产品接入层"，复用原则不变 |

## Output

设计方案输出结构：

```
# {业务}自迭代 Agent 系统设计
## 核心指标与行动边界
## 五层架构与职责契约（L1–L5）
## 双闭环流转（生产闭环 / 迭代闭环）
## 生产链路与 Human-in-the-loop 节点
## 可证伪交付物模板
## 四层记忆 Schema
## 无人值守门禁清单
## 风险与权衡
```

诊断报告输出结构：命中环节 → 根因 → 修复动作 → 优先级。
