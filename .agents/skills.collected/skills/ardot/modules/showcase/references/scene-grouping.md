# Scene Grouping / 场景分组判断

本文是 SKILL.md **Step 1.5（场景理解与分组）** 的详细版。
轴向（ROW/COLUMN/MATRIX）解决的是「整体怎么排」，但**「谁和谁分到同一个 group / 同一行 / 同一列」是另一个独立决策**，必须先于轴向判断完成。

历史教训：仅依据 cell 的 frame name、坐标位置或视觉相似度推断分组，极容易把用户已经组织好的语义打散，重排出不符合预期的展示区。**任何分组结论在没有与用户确认前都是假设，不是事实。**

---

## 分组判断的三条铁律

### 铁律 1：先尊重原始画布的"既有结构"

如果用户给的入口 node 本身就是一个 frame / section / group，**默认认为里面已经包含了用户的分组意图**，不要重新洗牌。

具体表现：

- 入口节点是一个**容器 frame**（不是一个画板列表），其中按行/列摆放了多个子 frame → 用户已经按某种维度（行 = ?, 列 = ?）做了排版，**优先沿用**。
- 入口节点是 Ardot **Section**（分区） → section 的命名 + 包含的画板就是一个天然 group。
- 子 frame 名称里带前缀/后缀（如 `登录-A`、`登录-B`、`购买页-V1`） → 命名前缀很可能就是 group key。

错误做法：看到子 frame 排在 3×2 网格里就直接套 MATRIX，自己重新决定哪行哪列是哪个语义。

### 铁律 2："看起来像"不等于"应该一组"

视觉相似（同尺寸、同 chrome、同色调）只代表它们是「同质 cell」，**不代表它们的业务语义属于同一个 group**。

例如：

- 6 个 1440×1080 整页稿，3 个购买页 + 2 个登录 + 1 个企业版弹窗 —— 只能说明它们都是 desktop 整页，**不能说明分组方式**：
  - 可能用户想按"页面类型"分组（购买/登录/企业版）
  - 可能用户想按"版本"分组（V1/V2）
  - 可能用户想按"流程步骤"分组（前置/中间/收尾）
  - 可能用户压根不想分组，平铺一行就够

只看 frame 的几何属性 **永远** 推不出唯一的分组方案。

### 铁律 3：不确定就停下问，不要"填空"

哪怕只有一点点不确定，也必须问用户。**"问错一个问题"的成本远低于"重排一个错的展示区"**。

不要用以下方式自欺欺人：

- "看起来 3×2 矩阵很合理" → 看起来合理 ≠ 用户期待
- "我先按 A 方案做，不对再改" → 重做的成本 ≥ 提前问的成本
- "frame 名字暗示了..." → 名字只是线索，不是确认
- "上下两行内容一样所以一定是 V1/V2" → 也可能是同一稿的两次复制，用户根本只想保留一份

## 三步确认流程

### Step A：盘点原始内容

先调用 `batch_read` 把入口节点的子结构读全（depth ≥ 2），记录：

- 子 frame 的**数量、命名、尺寸、相对位置**
- 是否存在**重复内容**（两个画板内部数据一致 → 可能是误复制，应提醒用户）
- 是否存在 Section / Group / 组件实例等**已有容器语义**

### Step B：列出"分组假设"清单

基于盘点结果，**至少列出 2 种可能的分组方案**，每种方案明确：

- group 数量
- 每个 group 的语义标签
- 每个 group 包含哪些 cell（用 nodeId 标注）
- 总体轴向（ROW / MATRIX）

如果只能想到 1 种合理方案，且**完全沿用原始画布的既有摆位**（铁律 1），可以跳过确认直接执行；但执行报告里要明确写"沿用原始 X×Y 排列"。

### Step C：让用户选择或修正

用宿主交互原语（`ask_followup_question` / `AskUserQuestion` 或宿主等价的选择题工具）提交选择题，必须包含：

1. 至少 2 个候选方案（A/B），每个方案给出 group 名称和 cell 归属
2. 一个 `自定义` 选项，让用户直接告诉你正确分组
3. 一个 `保持原样` 选项（如果原画布本身就有合理结构）

提问示例：

```text
我读到 6 个 1440×1080 整页稿，原始画布是 3×2 网格摆放。
分组方案备选：

A. 按页面类型 3 group × 2 cells（购买页 / 登录 / 企业版购买）
B. 按版本 2 group × 3 cells（V1: 上排 3 屏 / V2: 下排 3 屏）
C. 不分组，6 屏横排单 row（保持平铺）
D. 自定义（请直接告诉我正确分组）
```

**只有用户回答后**，才进入 Step 2（轴向判断）和 Step 3（生成骨架）。

---

## 何时可以跳过确认

满足以下**全部**条件时可以不问：

1. 用户消息中已经显式描述了分组（"按设备分 3 组：iPhone / iPad / Web"）
2. 入口节点本身是单一 Section，section 内画板数 ≤ 5 且全部是同一类型多状态
3. 原始画布已经是单行/单列摆放，没有矩阵结构

只要任意一条不满足，**必须走 Step C 确认**。

## 反例库

### 反例 1：3×2 网格被强行解读为"场景 × 变体"

原始画布：6 个 desktop 整页，3 列 × 2 行，列方向语义不一致（购买/登录/企业版各有自己的两版差异）。

错误处理：直接生成 3 group × 2 cells 的 MATRIX，每 group 强行套"V1/V2"小标题。

后果：用户实际是把"购买页"放第 1、3、4 位，"登录"放第 2、5 位，"企业版"放第 6 位——**列方向不是分组维度**，agent 自定义的语义反而打乱了用户的真实意图。

正确处理：列出 ≥2 个候选方案，让用户选。

### 反例 2：把"复制粘贴的同稿"当成"不同状态"

原始画布：A 屏被设计师为了对比临时复制了一份到 B 位置，两屏内容完全一样。

错误处理：把 A、B 当成 V1/V2 两个状态，给 B 起一个虚构的 mini-title（"V2"）。

正确处理：在盘点时识别"重复内容"，向用户确认是否要保留两份，还是合并为一份。

### 反例 3：忽略 Section 名称

原始画布：用户在 Ardot 里建了 3 个 Section：「公开版」「企业版」「定制版」，每个 section 内 2 屏。

错误处理：跨 section 全量收集 6 屏，重新按尺寸/状态分组。

正确处理：Section 名称就是 group label，section 内画板就是 group 的 cells，**完全沿用**。

## 与 Step 2（轴向判断）的关系

| 决策 | 解决什么 | 输入 |
|---|---|---|
| Step 1.5（本文）| **谁和谁一组** | 用户意图 + 原始画布结构 |
| Step 2（决策树）| **怎么排** | Step 1.5 输出的 group 列表 + cell 内容类型 |

Step 1.5 必须先完成。如果分组都没确认就跳到轴向，agent 会被迫"猜"分组，回到拍脑袋模式。
