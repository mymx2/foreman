# Agentic Game Dev

设计关卡工厂，而不是设计关卡；定义生成算法 + 参数 + Seed，让每一关都可溯源、可改造、可验收。

## Overview

把一款小游戏从模糊创意推到可上线产品的完整实操路径：调研 → 策划 → 美术/音频 → 编码 → 关卡 → 接入宿主。每环节给出可直接执行的做法与验收标准；人、AI 或人机混合执行均可，契约不变。

## Outcome Contract

- Outcome: 用户得到一份可执行的小游戏研发方案（按环节展开，含每环节的输入、做法、产出物与验收），或对当前卡住环节的具体解法。
- Done when: 方案覆盖到用户目标所需的全部环节；关卡方案具备可溯源/可改造/可验收三性；美术有一致性锚点机制；接入有明确的宿主协议。
- Evidence: GDD 章节、资产清单与依赖关系、关卡方案五章、难度曲线、壳应用分层、宿主协议通道。
- Output: 环节化研发方案或卡点修复清单。
- Authorization: 默认输出方案与契约；写代码、生成资产需用户明确要求。

## When to Use

- 从零做一款小游戏：只有一句话创意，不知从何下手。
- 研发卡在某环节：美术风格不统一、关卡有无解、游戏接不进宿主。
- 想批量产出小游戏原型验证玩法。

Not for: 大型游戏研发、游戏运营数据分析、纯理论游戏设计讨论。

## Process

1. **定玩法：以图代言，从发散到收敛。** "做一个消除类游戏"可能指糖果传奇、俄罗斯方块、连连看，文字描述成本高且易偏。做法：把创意扩成多组搜索词 → 并发搜图、去重取前 20 张 → 从图中指出方向（可多选）→ 分析选中图提取核心玩法机制、交互元素与胜负逻辑 → 用提取的关键词搜详细规则与攻略 → 同步挑出 2–3 张最佳美术参考图留待美术环节。完成标准：产出调研结论含玩法机制、核心循环、竞品现状、实现要点、美术参考图清单。
2. **写 GDD：信息密度优先。** 每段描述必须能被执行者直接消费，映射不到具体开发动作的描述不写。判据对照：合格句"玩家点击水果时，水果沿抛物线分裂为两半，得分 +1，由 Fruit.ts split() 实现"（能映射到实体、逻辑、数值）；噪声句"游戏要有爽快的切割感"（无法映射，删）。必备章节：概览（类型、核心循环、目标用户）、实体定义（对象、属性、状态流转）、操作与规则（输入映射、胜负条件）、道具与商业化（道具效果、变现点）、视觉风格定义（风格、配色、参考方向）、关卡设计（难度曲线、配置结构）、资产需求清单（程序资产 vs 素材资产分列，先定整体风格再列清单）。加载 `references/templates.md` 获取 GDD 填好的章节示例。完成标准：实体/规则/资产清单/风格定义分别能被编码、美术、关卡环节直接使用。
3. **产美术：先规划再生图，锚点保一致。** 加载 `references/art-pipeline.md` 执行。要点：先列完整资产清单（含朝向图、拆分图、依赖关系）再生成；两阶段拆分——先从工程视角定视角朝向与拆分方式（输出技术约束），再逐资产写视觉描述（画风/色彩/材质/形态）；生成按依赖定序、分组并发；三级锚点保风格一致（基准参考图 → 首张生成作风格锚 → 多状态对象用标准态）；全部完成后合成页面框架图，分析布局输出结构化描述给编码。局部修改走局部重生，不从头生成。完成标准：任意两张资产可回溯到同一风格锚点；编码拿到的含布局意图。
4. **产音频：按场景分类规划。** 加载 `references/art-pipeline.md` 的「音频生产线」节执行。从 GDD 梳理需要声音反馈的场景，按 BGM/交互/状态/UI 四类列清单（名称、描述、时长），逐个生成并试听校验。完成标准：清单覆盖 GDD 所有声音反馈点。
5. **写代码：壳应用 + 只写可变层。** 加载 `references/shell-and-protocol.md`。不从零搭工程：固化层（脚手架、分层架构、通用 UI、状态管理、关卡/道具通用接口、资源加载、事件总线）用模板预置，只写可变层——游戏对象与管理器、主场景逻辑、具体 UI 与交互、关卡配置、道具效果、资源定义。本步交付游戏壳；关卡工厂跑在另一个壳（关卡生成壳，第 6 步用），两个壳是同一"固化层+可变层"原则的两个实例。完成标准：游戏在宿主中原型可玩；实现的接口清单可供关卡环节读取。
6. **做关卡：设计关卡工厂而非关卡。**（本步是 self-iterating-system 通用层"内容设计 Agent"方法论在游戏域的实例化：类型→gameType，递变曲线→难度曲线。）方案严格五章：gameType、数据结构、生产方式、验证方式、难度曲线（如 30 关按 1-8/9-16/17-24/25-30 分四档递进）。生产方式按内容类型选（速查表）：布局类（消除/配对/数独）→ 算法生成，算法保证有解或毫秒级 BFS/DFS 验证；反应/动作类（切割/跳跃/打地鼠）→ 算法生成，行为模拟统计通过率；内容类（词库/题库/对话）→ LLM 生成，AI 校验合理性；视觉类（找不同/找茬）→ 文生图生成，行为模拟统计通过率；叙事/剧情类 → 有效性不可自动判定，走"人工抽检 + 发布后数据回收"第三条路，不承诺全自动。生成模式再答两问：判定快（含算法保证有效、毫秒级验证）→ 运行时生成；判定耗时 → 离线预生成 + 校验择优（含 Seed 溯源）。验证失败自动重试限次数，仍失败降级参数重生。加载 `references/templates.md` 获取关卡方案五章的填好示例。完成标准：五章齐全且每章可直接落地；关卡有唯一数据源。
7. **接宿主：三通道协议。** 统一数据查询（一个通用异步函数承载所有数据请求，游戏不关心数据来源）、标准生命周期回调（游戏单向通知宿主关键节点）、双向事件（上行/下行各一条固定通道承载自定义事件）。游戏独立构建部署，宿主零代码改动接入新游戏。完成标准：游戏在宿主场景内直接打开；新增一款游戏只需注册入口。
8. **验收三性。** 可溯源：任意一关用 Seed + 难度因子精确复现。可改造：修改明确到参数及目标值，改完用 Seed 逐关 diff 回归。可验收：预览蓝图与运行时复用同一条生成链路，看到的就是玩到的。方案设计阶段每条验证写明"怎么验"（如：用同一 Seed 跑两次生成，diff 结果应为空）；真实生成阶段逐条执行。完成标准：三项各有一条可操作的验证路径。

## 环境前提与降级

开工前确认可用能力，缺什么就走对应降级：

| 前提 | 缺失时的降级 |
| ---- | ---- |
| 图片搜索能力 | 让用户直接提供候选截图，或改用文字描述 + 关键词列表人工检索 |
| 生图服务 | 改用素材库采购/自制占位图，风格锚点机制不变（锚点换成选定素材） |
| 音频生成服务 | 用免版税音频库按四类清单选配，或砍音频需求仅留关键交互音效 |
| 宿主环境 | 游戏按独立 H5 交付，三通道协议退化为"URL 参数 + postMessage"两条；后续有宿主时再补全 |
| 壳应用模板 | 无模板可用时交付单工程 H5：固化层要求豁免，仅保留可变层的目录划分约定（对象/场景/UI/配置分目录），后续接入壳应用时按目录回迁 |
| 关卡可视化蓝图 | 用 JSON diff + 文本渲染的关卡截图替代，可验收原则不变 |

## Common Rationalizations

- "先把需求文档写细再开工" — 玩法方向靠指图收敛比文字描述准得多，细节留给 GDD。
- "GDD 越详细越好" — 映射不到开发动作的描述是噪声，会误导执行。
- "一张图一个 prompt 生就行" — 没有锚点的资产凑不成一个游戏，风格必然漂移。
- "关卡逐关手写配置" — 手写配置不可溯源也无法精确复现问题关；算法 + 参数 + Seed 才能逐关 diff。
- "每个游戏一个独立工程" — 业务外壳重复度 95%，模板固化通用能力后只写差异化逻辑。

## Red Flags

- 美术逐张独立生成，无风格锚点。
- 从零搭工程而不是在壳应用上填可变层。
- 关卡配置散落多份（配置文件一份、代码写死一份），无单一数据源。
- 宿主为每种数据单开接口，而非一个通用查询通道。
- 验证只验"能跑"，不验"有解/可通关"。
- 预览和运行时走两条生成链路，看到的和玩到的不是同一关。

## Verification

1. 调研结论含玩法机制与美术参考图。
2. GDD 每章能指认出消费它的环节。
3. 美术方案中每张资产声明了参考锚点（真实生成后可用依赖图回溯校验）。
4. 关卡方案含复现与 diff 方法（Seed 固定、参数可查）；真实生成后执行：同一 Seed 两次生成结果一致，改参数后逐关 diff 输出符合预期。
5. 新游戏接入宿主零代码改动（或有宿主缺失降级的明确说明）。

## Hard Rules

- **资产先规划再生图**：完整清单与依赖关系在前，生成在后。
- **关卡方案五章不可缺**：gameType、数据结构、生产方式、验证方式、难度曲线。
- **改动方案要落到参数**：不接受"建议降难度"，必须写清改哪个参数、目标值多少。
- **协议三通道**：通用查询、生命周期回调、双向事件，不为单个数据单开接口。

## Gotchas

| What happened | Rule |
| ------------- | ---- |
| 生图风格漂移 | 检查锚点链：基准参考 → 首张锚 → 标准态参考，断了就重建 |
| 新增实体不知参考谁 | 维护资产依赖图，新资产显式指定参考对象 |
| 关卡有的过不了 | 生产方式选错：非必然有解的必须走离线预生成 + 校验择优 |
| 更新一个游戏全量发版审核 | 游戏独立构建部署到 CDN，宿主无感；只有宿主业务变更才发版 |
| 数值调整也要发版 | 数值类走配置直调免发版，机制类才走完整上线流程 |

## Output

研发方案按 Process 八步输出，每步含输入/做法/产出物/验收；卡点修复按 Red Flags 逐条对照给出。
