# 壳应用与宿主协议

SKILL.md Process 第 5 步的工程契约：壳应用固化层/可变层划分、宿主与游戏通信协议。

## 壳应用：固化层 + 可变层

分层带来两个好处：不用从零搭建工程基础设施，只填游戏特有逻辑，大幅缩短编码时间；服务端能力完全复用（关卡查询推进、道具管理、商业化打通），新游戏接入无需重复开发。

小游戏生产涉及两个壳：游戏壳（SKILL.md 第 5 步，跑游戏本体）与关卡生成壳（第 6 步，跑关卡工厂与可视化验收）。两者是同一"固化层 + 可变层"原则的两个领域实例，固化内容各自不同，划分方法一致。

### 游戏壳应用

- 固化层：工程脚手架（游戏引擎 + 应用框架）、Controller 分层架构（业务/游戏/音频）、通用 UI 框架（Loading/导航栏/功能面板）、状态管理机制、通用接口设计（关卡查询推进、道具 CRUD）、资源加载链路、事件总线。
- 可变层：游戏对象和管理器、主场景逻辑、具体 UI 内容和交互、关卡配置数据、道具效果、资源定义。

### 关卡生成壳应用

- 固化层：周期 → 天 → 关 三级周期配置、通用服务接口（关卡/道具/广告链路）、前端路由框架和 gameType 注册机制、Schema 驱动的配置体系、构建发布流程。
- 可变层：具体游戏的关卡生成算法、验证逻辑、可视化页面、关卡 JSON 结构、参数曲线。

## 模块联邦（MF）场景化

对比"一个 H5 页面一个游戏"的传统模式：

| 场景 | 传统模式缺点 | MF 优势 |
| ---- | ---- | ---- |
| 业务逻辑 & 应用外壳 | 每个游戏工程重复实现同一套外壳 | 收敛到宿主一份，全局复用 |
| 新增一个游戏 | 新建工程 + 造外壳 + 页面发布；业务逻辑重复度 95% | 游戏模板只含游戏逻辑；只新增 remoteEntry 入口配置，宿主零代码改动 |
| 更新某个游戏 | 该游戏页面整体重新构建、发版、审核 | 游戏独立构建部署到 CDN，宿主无感 |
| 更新业务逻辑 | 每个游戏页都要开发、测试、发布 | 仅更新宿主业务代码 |
| 打开体验 | 页面级游戏，切换需跳页面 | 场景内直接打开，无明显加载体感 |

宿主按 asset 应用类型加载：MF 构建产物 + remoteEntry 入口。

## 宿主 ⇄ 游戏通信协议（三通道）

宿主侧通过 Props 回调 + Ref 命令与游戏通信；游戏内部走事件总线。

1. **统一数据查询通道**（游戏问、宿主答）：不为每种数据设计一个接口，用一个通用异步函数（如 queryGameConfig）承载所有数据请求。宿主侧自由决定数据来源，游戏侧完全不关心数据从哪来，只负责消费。
2. **标准生命周期回调**（游戏 → 宿主，单向通知）：onReady / onGameStart / onGameEnd 等关键节点，由模板统一封装回调函数。
3. **双向事件协议**：所有业务自定义事件走两条固定通道——上行 app:event（游戏 emit，宿主 onEvent(name, payload) 接收）；下行 host:event（宿主 sendHostEvent(name, payload)，游戏 on('host:event', handler) 监听）。通道固定、事件自定义，保障协议规范性与可扩展性。

## MF 契约（关卡场景）

宿主默认只下发当前关卡数 & 总关卡数；游戏依据通关进度在本地动态生成关卡，或直接使用内置预制关卡。两种模式共同遵守这一条契约。
