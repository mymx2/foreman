# PSD 设计制作规范（通用）

新建稿件和重构旧稿都按这份规范走。目标是三件事：稿子可维护、能交付、每条数值可复跑验收。

规范只给默认值。**项目 spec 优先**：用户给了画布、列数、间距、命名模板，以用户为准，不要用规范覆盖。

## 0. 三条硬底线

1. **重构时原稿只读**。另存规范稿再改，保留原稿 SHA256，结束复核未变。
2. **视觉验收和结构验收都要过**。像素一致只证明渲染一样，层树可能仍然不可维护。
3. **改完必复核**。`doc.inspect` 看到目标字段才算生效；属性回显不等于生效，蒙版、混合模式、智能对象能让改动静默消失。

## 1. 画布

| 用途 | 建议尺寸 | 分辨率 | 色彩模式 |
| --- | --- | --- | --- |
| Web 桌面稿 | 1920×1080 | 72 ppi | RGB |
| Web 内容区 | 1440 宽（内容区 1200，左右各 120） | 72 ppi | RGB |
| 移动端 | 750×1334（@2x）或 390×844（@1x） | 72 ppi | RGB |
| 社媒方图 | 1080×1080 | 72 ppi | RGB |
| 社媒竖图 | 1080×1920 | 72 ppi | RGB |
| 印刷 A4 | 2480×3508 | 300 ppi | CMYK |

- 尺寸来源：行业通行值（Web/Figma 社区惯例与 VectoUI 制图规范），**不是官方强制标准**；项目 spec 优先。
- **一个项目约定一个画布尺寸，中途不改**。改了栅格、间距、切图全部要重算。
- 交付引擎（Unity 等）时画布尺寸还要与引擎 UI 根节点一致。

## 2. 栅格与间距

**间距刻度**：4 / 8 / 12 / 16 / 24 / 32 / 40 / 48 / 64（8pt 体系）。出现 13、19、22 这类孤儿数值，先回刻度找最接近的合法值。

**取值惯例**：
- 组件内 padding：8 / 12 / 16
- 模块外边距：16 / 24 / 32
- 列间距 gutter：16 或 24

**列网格公式**：

```
columnWidth = (frameWidth - margin*2 - gutter*(columnCount-1)) / columnCount
第 i 列 x = margin + (columnWidth + gutter) * i
跨 n 列 width = columnWidth*n + gutter*(n-1)
```

**列宽取 8 的倍数**。真正要保证的是**步距 `(colW + gutter)` 为 8 的倍数**——列起点是 `margin + 步距*i`，只有步距合规，所有列起点才会落在 8pt 上。gutter 本身是 8 的倍数时，列宽取 8 的倍数即可。

**宽度必须取整列值**。元素宽度只能是「跨整列」的值：

```
跨 n 列 width = colW*n + gutter*(n-1)    条目的右边界 = 列起点 + colW
```

1200/80/24/12（列宽 64、步距 88）的合法宽度为 `64, 152, 240, 328, 416, 504, 592, 680, 768, 856, 944, 1032`。取 344 时 x 仍在列起点上，但右边界 424 越过列线 16px，视觉上就是没对齐。判定必须同时看 x、宽度、右边界三项。

**不要逐值吸附 8pt**，也不要只做向下取整 —— 1440/120/24/12 若列宽取 78（向下取整），步距 102 不是 8 的倍数，列起点变成 120/222/324 参差不齐；列宽取 72 时步距 96，列起点 120/216/312 全合规。

`scripts/layout-design.py calc` 验证过的五组（右侧余量留给页边）：

| 画布 | margin | gutter | 列数 | 8pt 列宽 | 步距 | 列起点 | 右余 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1200 | 80 | 24 | 12 | 64 | 88 | 80/168/256… | 8 |
| 1440 | 120 | 24 | 12 | 72 | 96 | 120/216/312… | 72 |
| 1920 | 80 | 24 | 12 | 120 | 144 | 80/224/368… | 56 |
| 1080 | 16 | 16 | 4 | 248 | 264 | 16/280/544/808 | 8 |
| 750 | 16 | 16 | 4 | 160 | 176 | 16/192/368/544 | 30 |

**列数与边距默认值**：Web 12 列 / margin 80 / gutter 24；移动端 4 列 / margin 16 / gutter 16。来源是 Web/Figma 社区通行配置，不是官方标准。

## 3. 层级契约（节点树，类似 HTML DOM）

**层级就是节点树**：一个页面由若干区块组成，区块由若干组件组成，组件由若干元素组成。显示/隐藏、删除、移动都以**节点**为单位 —— 删一张卡片只删一个组，不必分别去"文字/装饰/图标"里找散落的层。

```
页面_<名称>              1 个（单页面稿可省略，直接用 区块_ 开头）
  区块_<名称>            N 个（横向分区：头部/首屏/内容/底部）
    组件_<名称>          N 个（语义单元：卡片_01/按钮_提交/图标_主视觉）
      元素（叶子层）       N 个，命名带类型语义
```

**深度不设硬限**。组件内部再嵌套组件（弹窗 → 表单项 → 输入框 → 图标）是正常结构，机械地卡层数只会逼出扁平化的烂稿。控制嵌套用另外两条规则：禁止空组、禁止单子层冗余组。**节点组（页面_/区块_/组件_/参考_/版本_）是语义容器，单元素正常，不判冗余**；只有非节点组的单子层组才判 MEDIUM。`psd-audit.py` 的 `maxDepth` 只是参考统计，需要硬限时才显式传 `--max-depth N`。

### 元素命名前缀（强制，靠前缀区分类型，不靠顺序）

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `文字_` | 文字层（标题/描述/正文） | `文字_主标题`、`文字_描述` |
| `图标_` | 小图形、装饰性图标 | `图标_主视觉`、`图标_箭头` |
| `图片_` | 位图、照片、插图 | `图片_产品` |
| `形状_` | 矢量形状、分隔线、边框 | `形状_分割线` |
| `效果_` | 光效、阴影、氛围 | `效果_光晕`、`效果_投影` |
| `背景_` | 组件/区块的底色或底图 | `背景_卡片底`、`背景_渐变` |
| `参考_` | 对照稿、标注、隐藏参考 | `参考_原稿平图` |

组名也按前缀：`页面_x` / `区块_x` / `组件_x` / `参考_x` / `版本_x`。

### 层级边界矩阵（什么能放在什么下面）

| 父组 ↓ \ 子层 → | `区块_` | `组件_` | 元素前缀 | `参考_` | `版本_` |
| --- | --- | --- | --- | --- | --- |
| `页面_` | ✓ | ✓ | ✓ | ✓ | ✗ |
| `区块_` | ✓（嵌套区块） | ✓ | ✓（简单内容可直放） | ✓ | ✗ |
| `组件_` | ✗ | ✓（子组件） | ✓ | ✓ | ✗ |
| `参考_` | ✗ | ✗ | ✓ | ✗ | ✗ |
| `版本_` | ✓ | ✓ | ✓ | ✓ | ✗ |

根层只允许 `页面_`/`区块_`/`参考_`/`版本_` 组，元素层直放根层判 HIGH（`ROOT_LOOSE_LAYER`）。边界由 `scripts/psd_contract.py` 的 `ALLOW_NESTED` 单点定义，两脚本共用。

### 视觉层序

同组内元素的面板顺序 = 视觉上下层序（面板越靠上视觉越上层）。**`背景_` 元素必须在组内最底层**（doc.inspect 自上而下即末尾，psd_tools 自下而上即开头）。

### 规则

- **根层必须是 `页面_` 或 `区块_` 开头的组**（或多页时 `页面_*` 包装、多版本 `版本_*` 包装）。根层散落的元素层会被判 HIGH。
- **同组内元素用类型前缀命名**：`文字_`/`图标_`/`背景_` 等。这样既能按节点整体操作，也能按类型全局搜索。
- **未用到的前缀不建空组**，空组判 HIGH。
- **隐藏内容只允许在 `参考_*` 组或 `版本_*` 包装下**，其他位置的隐藏层判 MEDIUM。
- **同组内元素前后层序 = 视觉上下层序**：面板越靠上视觉越上层。要压过某层改层序，用 `layer.moveTo {target, position:"above"|"below"|"into"}`。
- **新层不会自动进组**。即使先选中组再建层，新层也是与组平级；每建一层都要 `layer.moveTo {layer:<新层>, target:<组>, position:"into"}`。
- **建组顺序反向**：新建层默认落在当前层上方。节点树中组顺序=视觉层级，建议先建底层（`背景_` 元素）再往上堆叠。

## 4. 命名

- 模板 `<前缀>_<语义>[_<状态>]`：`文字_主标题`、`图标_箭头`、`组件_卡片_01`、`背景_渐变`。前缀见第 3 节。
- **禁止**：默认名（`图层 1`、`组 2`、`文本 1`、`Layer 1`、`Group 2`、`Copy`、`未命名`）、空名、首尾空格、`副本`/`拷贝`/`copy` 后缀。
- 同一父级不重名，重名用 `_01`、`_02` 区分。
- **交付引擎时只能用英文+数字+下划线**（`btn_confirm_01`），中文和特殊符号会让引擎无法识别。不出 PSD 只出图时中文命名可以用，但要全项目一致。

## 5. 层树

- 所有内容进组，根层不允许散落图层。空组清理掉；单子层冗余组只针对非节点组（节点组单元素是语义容器，保留）。
- 深度不设硬限；嵌套合理性由「无空组」「无非节点组单子层冗余组」保证。
- 同一组超过 30 个平级层就按语义再分组（软上限）。
- 隐藏层只允许在 `参考` 或 `版本_*` 下，其他位置的隐藏内容删除或移入版本组并登记。**定稿删除所有隐藏废层**。
- `文字` 组只放文字层；出现像素层/智能对象按「可能已栅格化」处理，优先重打。
- 抠图用蒙版，不擦像素。
- 复杂合成、重复素材转智能对象。
- **混合模式**：叠加、滤色、颜色减淡这类复杂模式，引擎端 UI 材质通常不支持，交付前必须和底图一起烘焙合并成单图。

## 6. 文字

- 保持文字层可编辑，**不栅格化**。
- 行高约为字号的 1.4–1.7 倍：标题偏紧、正文偏松（行业通行值）。
- 多行文字画固定尺寸文本框，不让文字溢出或随内容无限拉长。
- 字体名与实际可用字体一致；缺字体出候选让用户定，**不自动换近似字体**。
- 商用授权不明的字体不进交付。

## 7. 布局怎么执行

```
定 spec → 铺参考线 → 从底向上建组 → 逐层建 + moveTo into → 算坐标 → translate 写回 → align/distribute 校正 → inspect 复核
```

1. `view.newGuideLayout {columns, width:<列宽>, gutter, margin, clearExisting:true}` 铺参考线。
   **`width` 是单列宽，不是画布宽**。传画布宽会报 "count, size and gutter must fit inside the target margins"，且列宽超出可用宽度时同样报错。
   列宽取第 2 节算出的 8pt 列宽。
   **参考线不回显在 `doc.inspect`，也不出现在 `doc.render`**，headless 下只能信返回的条数。
2. **从底向上建根组**（背景先建、参考最后建），未用类别不建。
3. **逐层建并立刻 `moveTo into`**。新层不会自动进组；`layer.select` 只决定插入位置。
4. `doc.inspect` 读每层 bounds，格式是 **`[x, y, w, h]`**。`type.create` 的 x/y 是基线锚点，实际 bounds 会偏，以 inspect 为准再补 `translate`。
5. 按第 2 节公式算目标坐标（用 `layout-design.py calc`）。
6. `layer.translate {layer, dx: 目标x-当前x, dy: 目标y-当前y}` 写回。要改尺寸或精确摆四角用 `edit.transform {rect|quad|matrix}`。
7. `layer.align.*` / `layer.distribute.*` 校正残余误差。这两个作用于**图层选区**：`layer.select {layer:id}` 起选、`mode:"add"` 累加；操作前先 `select.deselect` 清像素选区。
8. `doc.inspect` 复核每层 bounds 命中目标；`layout-design.py check` + `psd-audit.py audit --strict` 双验收。

**布局是静态结果，不是活容器**：PhotoCraft 没有 Figma 的 HUG/FILL 和响应式约束，改了内容尺寸不会自动重排，要重算重摆。

## 8. 验收

| 维度 | 命令 | 通过标准 |
| --- | --- | --- |
| 结构（读 PSD） | `scripts/psd-audit.py audit <稿> --strict --json` | `strictOk: true`；CRITICAL/HIGH/MEDIUM 为 0，LOW 逐条有结论 |
| 结构与布局（读 inspect JSON） | `scripts/layout-design.py check --spec <spec.json> --inspect <inspect.json> [--strict]` | 退出码 0 |
| 视觉 | `scripts/psd-compare.py <旧渲染> <新渲染>` | `result` 为 `identical`；`differs` 时定位差异并解释 |
| 保存 | `doc.save {path}` | 回执 `path` 存在，`warnings` 为空或逐条解释 |
| 交付 | 描述文件 + `fonts/` 副本 | 每稿有同名 `.md`，字体哈希可核对 |

**inspect JSON 的两个来源结构不同**：headless `doc.inspect` 直接给 `layers` + `kind`；`photocraft-cli info --compact` 也能出层树，但字段需转换，**转换时务必保留 `kind`**（`Type`/`Pixel`/`Group`）—— `check` 靠它区分文字层（文字按内容定宽，不参与跨列宽度判定）。丢掉 `kind` 会把文字层当像素层，误报宽度不符。

- **spec.json 必须带 `width` 和 `height`**：宽度算栅格列，两者一起识别「铺满画布的底图层」并豁免其栅格检查（底色本来就该铺满，不该被要求对齐列）。
- `check` 覆盖：根组命名（应以 `页面_`/`区块_`/`参考_`/`版本_` 开头）、命名（默认名/同级重名 = HIGH、副本后缀 = MEDIUM）、空组（HIGH）、根层散落、隐藏层位置、x 落列、宽度是否为合法跨列值、右边界是否落在列边界、y 与间距为 8pt 倍数、**坐标是否为负（HIGH）**、**水平/垂直越界（HIGH）**、**同父级元素重叠（HIGH）**。
- 文字层按内容定宽，不参与宽度判定，但起点仍要对齐列；**文字层的高度与下边界也不参与 8pt 判定**（字形度量决定，不由排版控制）。
- `psd-audit.py` 覆盖更多结构项（文字可编辑性、智能对象、隐藏层等），但只读 PSD 文件、读不了 headless 的 inspect JSON —— **两个脚本输入源不同，不能互相替代**。

**两个脚本都查不了的，必须人工/目视验收**：颜色对比度（文字与背景、卡片与底色是否分得开）、字号层级与行高、文字是否溢出文本框、视觉层级是否与语义匹配、留白比例、切图完备性、混合模式兼容性、智能对象的外部素材是否缺失、色彩模式与分辨率是否匹配交付目标。脚本能保证的是几何与结构，**不保证好看、可读、能交付到目标引擎**。
- 审计脚本读 PSD 字体表，字体**安装状态以 `type.fonts` / `type.resolveMissingFonts` 为准**。
- 严重度分级：CRITICAL 无法交付、HIGH 必须修、MEDIUM 应修或说明、LOW 建议；`--strict` 时 MEDIUM 也算失败。

## 与规范化/复刻模式的分工

- 本文 = **做成什么样**（通用设计制作规范）。
- `references/psd-normalization.md` = **怎么把烂稿修成规范稿**（重构流程与验收）。
- 新建稿件按本文第 1–7 节做，收尾按第 8 节验收；重构旧稿走规范化/复刻模式，目标结构同样遵守本文第 3–5 节。
